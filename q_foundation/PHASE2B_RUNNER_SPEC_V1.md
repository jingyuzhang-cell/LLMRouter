# PHASE2B 六要素 Runner 实施规格（v1，供操作者审阅；未写任何代码）

> 第一步交付物。约束：零模型调用、零代码修改、零实验执行。每要素含：数据结构 / 执行时点 / 验证断言 / 失败条件 / 验收标准。适用于任何未来获授权批次（首个适用对象=PHASE2B Static-π 基线）。**本规格批准前不实施。**

## 要素一：载荷持久化

- **数据结构**：每次调用两个原始文件——`payloads/{run_id}/{node_id}/{call_id}.req.json`（完整请求：url、headers 脱敏后、body 原文）与 `{call_id}.resp.json`（完整响应：状态码、响应体原文、usage、latency、model_id）。字节级原样，不做任何清洗。
- **执行时点**：请求文件**先写后发**（write-ahead：未发送即崩溃会留下无响应的请求文件，可检测）；响应文件在收到后、**解析前**落盘。
- **验证断言**：`sha256(文件字节) == 台账声明哈希`；请求-响应经 `call_id` 一一配对。
- **失败条件**：哈希不匹配 / 响应文件缺失 / 写入异常。
- **验收标准**：100% 调用拥有成对载荷；审计者对任意样本独立重算哈希通过。**修复 Batch-1 缺口：请求体从未持久化 → 今后逐调用全量留存。**

## 要素二：双哈希与关联 ID

- **数据结构**：台账行增 `{call_id: uuid4, request_sha256, response_sha256, run_id, node_id, attempt, retry_of: null|call_id}`；`call_id` 每次尝试唯一（重试生成新 id 并链接前次）。
- **执行时点**：请求哈希在序列化完成后、发送前计算；响应哈希在落盘时计算。
- **验证断言**：`sha256(重读载荷文件) == 声明值`；`call_id` 无重复；每行同时具双哈希。
- **失败条件**：任一断言失败。
- **验收标准**：审计脚本全量重算通过；零重复 id；重试链完整可追溯。**修复"声明哈希=载荷哈希"无从验证的问题。**

## 要素三：模型真实身份验证

- **数据结构**：每调用持久化 `{model_config_sent（请求体 model 字段）, model_id_returned（响应体 model 字段）, expected_identity（冻结值）, identity_match: bool}`。
- **执行时点**：响应解析后、输出被接受前。
- **验证断言**：请求 model 字段 == 冻结标识；实返 model_id 含冻结标识字符串。
- **失败条件**：任一不匹配 → **按执行边界裁定②整批即停**（保留全部记录，重新裁定模型组合；禁止静默替换或自动切换备选）。
- **验收标准**：100% 调用身份核验通过；任何不匹配触发的是停批而非换模。

## 要素四：实验台账关联

- **数据结构**：台账行增 `{run_id（task|repeat|arm）, node_id, phase, budget_snapshot:{calls_used,tokens_used,cny_used}, wall_clock}`；每 run 的 manifest：`{run_id, seed, upstream_sha256（如 r1 快照）, prompt_sha256, contract_sha256, started_at, ended_at}`。
- **执行时点**：逐调用追加；run 起止各记一条边界行。
- **验证断言**：每个载荷文件可由台账 call_id 唯一定位，反之每个台账行有载荷（双向闭包）；run manifest 的合同/提示哈希 == 冻结值；预算快照与台账累计一致。
- **失败条件**：孤儿载荷 / 无载荷台账行 / 哈希与冻结值不符 / 预算对不上。
- **验收标准**：双向闭包 100%；预算逐行重算精确一致。

## 要素五：独立审计

- **机制**：独立脚本 `audit.py`（与 runner 分离，只读冻结产物）重算：①全部载荷双哈希；②身份匹配；③台账-载荷双向闭包；④预算算术；⑤**提示重建等值**（`sha256(由持久化上游链确定性重建的提示) == 该调用 request_sha256`——修复 Batch-1"重建≠实发"无从检测的缺口）；⑥**J 层锚点继承**（J 输出的证据五元组 quote/哈希必须逐字出现在上游 E 输出中——"照抄"而非"编造"）；⑦sink 引文经评价器哈希跨度核验。
- **执行时点**：每 run 结束自动执行；**任何报告生成前强制执行**（报告生成以 audit exit 0 为前置）。
- **验证断言**：audit 退出码 0。
- **失败条件**：任一子项 FAIL → 该 run 标记 AUDIT_FAILED，结果不释放（终点式，无中途授权——沿用冻结规则）。
- **验收标准**：审计者（你或独立第三方）可从冻结产物独立重跑 audit.py 并复现 exit 0；抽样 N 个载荷人工核对与脚本一致。

## 要素六：异常处理与失败闭锁

- **数据结构**：`FAILLOCK.json` `{reason, call_id, ts, state_snapshot_paths}`；写入后 runner 在**每次调用前**检查该文件，存在即拒绝发出任何请求。
- **执行时点**：要素一至五任一失败条件触发时、预算预检触顶时、身份不匹配时。
- **验证断言**：闭锁后追加调用数 == 0（audit 核验）。
- **失败条件**：闭锁存在仍尝试调用 = 终局违规。
- **验收标准**：以**注入式故障演练**（零模型调用：在干跑 harness 中模拟哈希不匹配/身份不符/预算触顶）证明闭锁触发并阻断。

## 横切约束

1. 本规格**不追溯适用于历史批次**（"历史不因审计能力完善获补充证据或追溯 PASS"）。
2. 实施顺序：你审规格 → 批准 → 写代码（runner2→runner3 升级）→ 干跑演练（零调用验证六要素）→ 你验审计链 → 才可申请模型调用。
3. 预算守卫沿用：逐调用预检 + 逐组预留 + 现金绝对硬顶 + 终点式熔断。
