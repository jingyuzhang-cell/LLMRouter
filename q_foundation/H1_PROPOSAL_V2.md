# H1 真实实验方案 V2（2026-10-31，零调用）

**核心问题**：在持久性合并验证合同异常下，结构重构 Z 是否能够在 R+π 已经具备恢复能力的基础上，进一步改善验证完成率和终端质量？

**修正**：V1 的三个问题（预算矛盾 / 缺 R+π 对照 / 合同语义等价审计）全部解决。

## 二、拆分语义等价审计（修正：零调用已执行）

### 审计结果

| 检查项 | 结果 | 证据 |
|---|---|---|
| 原合同检查项保留 | ✓ | 子节点 subtask 包含原 subtask 完整文本 |
| 子验证合同覆盖 | ✓ | e05_chk_a/b 均为 kind=verification，各自验证一个上游 |
| **跨来源一致性保留** | ✓ | **report 节点仍消费两个子验证输出**（e05_rpt deps=[e05_chk_a, e05_chk_b]） |
| 下游消费正确 | ✓ | report 依赖 2 个子验证，不是只依赖 1 个 |
| 证据要求不降低 | ✓ | 子节点使用同一 kind 和合同要求 |

### 关键证明

**拆分后 report 节点依赖 [e05_chk_a, e05_chk_b]**——两个子验证的输出**都**流向最终报告。这意味着：

1. **跨来源一致性检查转移到了 report 层**——报告节点消费两个独立验证的结果，相当于做最终综合核验
2. **不是降低验证标准**——每个子验证仍按原合同的验证要求执行（subtask 文本保留）
3. **信息不丢失**——report 看到两个来源的验证结论，而非只看到一个

**结论**：SPLIT_VERIFY 改变的是验证的组织方式（合并→分别→报告综合），不降低验证要求。**公平性成立。**

## 五、终端质量评价（不变，补充统计表述）

### 报告维度

| 维度 | 指标 |
|---|---|
| 报告生成率 | COMPLETE / 总 runs（各组分别统计） |

| C | 实际 tokens（分模型） |

### 选择偏差处理
如果某组 COMPLETE 数远少于另一组：
- **不**直接比较 COMPLETE-only 的 Q 均值
- **必须**同时报告生成率和条件 Q
- 读者可以据此判断选择偏差的程度

### 评分标准
- 主选：quality_v4（**仅当独立复审通过**）
- 备选：同任务、同 Silver/裁决参考、同公式
- E08 参考仅适用于 TGV-T2
