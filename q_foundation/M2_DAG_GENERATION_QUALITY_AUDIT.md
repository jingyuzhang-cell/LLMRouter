## 五维度评价

### 维度 1：任务覆盖

| 检查项 | Auto | SC 手工 |
|---|---|---|
| 核心 pipeline 完整 | ✓ index→extracts→timeline→entity→verify→report | ✓ index→extracts×2→reasoning+timeline→verify→report |
| 多文档分源抽取 | **✗ 单一 extracts 节点覆盖所有文档** | **✓ 每文档一个 extracts 节点** |
| 验证节点双亲异类性 | △ factcheck_full 依赖 timeline+entity（异类） | ✓ verification 依赖 reasoning+timeline（异类） |

**发现：自动 DAG 在多文档任务上缺失分源抽取——单一 extracts 节点必须同时处理多份文档，可能降低每份文档的抽取质量。**

### 维度 2：依赖正确性

两者均为钻石型结构（extracts → 分叉 → 汇合验证 → 报告），拓扑正确。

**但 SC 手工 DAG 有一个自身缺陷**：e1_fin (reasoning) 仅依赖 e1_ext_pen（单侧 extracts），可能丢失另一侧文档信息。

### 维度 3：节点粒度

| | Auto | SC |
|---|---|---|
| extracts 节点数 | 1（所有文档共用） | 2（每文档一个） |
| 合同粒度 | 简短 goal 文本 | 详细 subtask 指令 |

**权衡**：Auto 粒度更粗 = 更少节点 = 更低成本，但每个节点任务更重。SC 粒度更细 = 更高成本，但节点专一性更强。

### 维度 4：合同完整性

| | Auto | SC |
|---|---|---|
| 节点说明 | 简短 goal（如"抽取…日期文号"） | 详细 subtask（含具体抽取要求） |
| 合同系统 | 通用 kind→contract 映射 | delta 合同系统（SYS_R9，含继承/增量/验证规则） |
| 证据绑定 | doc_ids 列表 | span 级哈希绑定 |

**Auto DAG 缺乏合同级质量保障**——节点执行依赖通用 kind 映射，没有任务特定的合同约束。

### 维度 5：结构效率

两者深度相同（5 层），关键路径长度相当。Auto 用更少节点（6 vs 7），成本更低但专一性牺牲。

---

## 关键发现（对研究主线的影响）

### 发现 1：自动 DAG 的结构性缺陷是"分源缺失"

对于**多文档跨来源任务**（我们的核心场景），自动 DAG 的单一 extracts 节点可能导致：
- 每份文档的抽取深度不足
- 跨文档信息在抽取阶段就被混合，后续难以分源验证
- 与 Z(SPLIT_VERIFY) 的结构重构空间冲突——如果 extracts 不分源，verification 的双亲就是同类

**含义**：M2 的改进方向不是生成更多节点，而是让 planner 理解多文档任务的分源需求。

### 发现 2：SC 手工 DAG 自身也有结构问题

e1_fin 仅依赖 e1_ext_pen（单侧），可能丢失 e1_ext_proc 的信息。**这说明手工设计也不完美——M2 的评价框架应该同等适用于手工 DAG。**

### 发现 3：当前所有后续实验依赖手工 DAG

从 Stage-C 到 H1，全部实验使用手工设计的 SC/TGV DAG。**如果最终系统需要自动生成 DAG，M2 的质量差距必须先解决。**

---

## M2 改进建议（零调用设计）

1. **分源抽取规则**：planner 应为每份证据文档生成独立的 extracts 节点
2. **合同模板**：为常见节点类型建立任务特定合同模板（而非通用映射）
3. **质量自检**：生成后自动检查验证节点双亲异类性、extracts 分源覆盖
4. **SC DAG 修正**：e1_fin 应依赖两个 extracts 节点（当前仅一个）

## M2 在完整系统中的定位

```
M2 (DAG 生成) → 决定初始执行图的合理性
  ↓
M4 (静态调度) → 在合理的图上分配模型
  ↓
M5 (动态调度) → 异常后调整 Z/R/π
  ↓
M6 (反馈更新) → 从结果学习改进 → 反馈至 M2 和 M4
  ↓
M7 (多目标优化) → 评估整体 Q/C/L 效果
```

**M2 的质量上限决定了整个系统的质量上限。如果 DAG 分解不合理，后续调度的收益空间就被压缩。**
