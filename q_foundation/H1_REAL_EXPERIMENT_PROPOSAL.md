能否通过改变验证任务的组织方式，提高任务恢复成功率和终端质量，并控制额外成本与时延？

**定位**：小规模机制验证（探索性），非确认性统计实验。

## 三、故障注入协议（关键设计）

### 故障定义
- **位置**：验证节点（e1_chk / e3_chk / e05_chk / e08_chk）
- **类型**：持久执行合同异常（`type='contract'`）
- **语义**：该节点的合并合同（消费多个异类上游输出并生成综合验证结论）持续失败

### 为什么重试无法解决
- 持久 = 无论重试多少次，同一合同约束下的执行继续失败
- 模拟真实场景：合并验证逻辑的系统性缺陷（如 JSON schema 要求同时处理两种异构输入）

### 为什么换模型无法解决
- 故障是合同级的（结构性），不是模型级的
- 任何模型在该合同约束下都会遇到同样的组合困难

### 为什么拆分能解决（公平性论证）
- 拆分后每个子验证节点只消费**一个**上游的输出
- 合同从"综合验证异构输入"简化为"验证单一类型输入"
- **原故障节点被替换，不是被豁免**——故障作用于合并合同，不作用于单源验证
- 拆分后的子节点使用自己的合同，必须成功才能继续

### ⚠️ 公平性审查要点
**必须确认**：拆分不是"绕过故障的特权通道"。如果故障定义为"所有验证调用必败"，拆分子节点也
应失败。在本设计中，故障定义为"合并验证合同失败"——这是合理的业务场景（合并复杂输入时出现
系统性组合困难），而非人为为 Z 开路。

## 四、终端质量评价

### 评分标准（统一）
- **主选**（若 P0 独立复审通过）：quality_v4 六维评分
- **备选**（若 P0 未通过复审）：同任务、同 Silver/裁决参考、同覆盖公式
- **E08 参考仅适用于 TGV-T2**

### 四个报告维度

| 维度 | 指标 | 说明 |
|---|---|---|
| Q | 终端事实质量 | 参考覆盖率 / quality_v4 Q_final |
| C | 实际调用成本 | tokens（分模型）、API 调用次数 |
| L | 实际端到端时延 | makespan |
| R | 执行可靠性 | COMPLETE/INCOMPLETE、合同失败次数 |

### INCOMPLETE 处理
- 报告生成率单独统计
- INCOMPLETE 的 Q 不计入 COMPLETE 的质量均值
- 除非预注册另有规定，不默认 Q=0

## 六、验收门槛

| 门槛 | 问题 | 通过条件 |
|---|---|---|
| **T1 结构恢复** | Z+R 在真实执行中能否完成子验证并生成报告？ | G4/G5 报告生成率 > G1/G2/G3 |
| **T2 终端质量** | 重构后的报告是否真正提高事实正确性？ | G4/G5 Q_terminal > G1/G2（在 COMPLETE 条件下） |
| **T3 Q/C/L 联合** | 收益是否在可接受成本内？ | G4/G5 成本增幅 ≤ 参考线（+40%），按期率 ≥ G2 |

三个门槛不能互相替代。
