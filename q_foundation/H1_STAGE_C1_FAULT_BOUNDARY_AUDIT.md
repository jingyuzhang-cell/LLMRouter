## 详细发现

### 1. 故障绑定机制

```python
def inject_result(anomalies, nid, result):
    inj = anomalies.get(nid)  # ← 按节点 ID 匹配
    if inj['type'] == 'contract':
        return dict(result, success=False, ...)  # ← 无条件标记失败
```

**绑定的是节点 ID，不是合同类型或执行语义。** 意味着：
- 对该节点 ID 的任何调用（无论模型、无论内容）都会被标记失败
- 原始 docstring 明确说 "narrower split successors use different node ids and are not injected"

### 2. 拆分后子节点不继承故障

`apply_z` 创建 `e1_chk_a` 和 `e1_chk_b`（新 ID），原节点 `e1_chk` 被移除。anomalies 字典中只有 `e1_chk`——新 ID 不受影响。

### 3. 公平性判定（含限定条件）

**公平的合理解释**：故障代表合并验证接口的系统性缺陷——两个异类上游（timeline + reasoning）同时输入时出现 schema 不兼容或组合困难。拆分为单源验证消除了不兼容。

**类比**：数据集成管道中，合并步骤在组合两种数据格式时出现 schema 不兼容——拆分为独立处理路径消除了不兼容。

**必须限定的范围**：
- ✅ 可外推：合并接口存在格式/组合级缺陷，拆分可恢复
- ❌ 不可外推：所有"验证逻辑失败"都能通过拆分解决
- ❌ 不可外推：所有持久节点故障都适合用 Z 恢复

**建议术语修正**：将此故障类型从 "persistent contract fault" 改为 **"merge-contract fault"**（合并合同故障），明确其作用域。

### 4. 跨来源一致性完整保留

report 节点在拆分后：
- 依赖 `[e1_chk_a, e1_chk_b]`（两个子验证输出）
- REPORT_SYS_R9 的跨文档比较合同独立存在
- G5 实际输出 4 个跨来源比较（立案日期一致、告知日期一致、退市认定一致等）
- 终端事实覆盖两个来源文档（zzd_notice_2019 + zzd_penalty_2020）

**结论：跨来源一致性检查完整保留在 report 层，拆分未降低验证标准。**

### 5. 成本核算完整

G5（Z+R）的 9 次调用逐条审计：

| 类别 | 调用数 | Token | 说明 |
|---|---|---|---|
| 正常前缀 | 5 | 6,501 | idx + extracts + fin + tl |
| 失败重试 | 1 | 1,850 | e1_chk 第 1 次尝试（合并合同失败） |
| 拆分子节点 | 2 | 2,778 | e1_chk_a + e1_chk_b |
| 报告 | 1 | 3,698 | e1_rpt |
| **合计** | **9** | **14,827** | **与 run-level tokens 精确一致** |

**全部成本已计入**——无遗漏的隐藏调用。Z 的额外成本（拆分子节点 2,778 tok）远低于 R-only 的无效重试浪费（4 次 × ~1,850 = ~7,400 tok）。

## 对下一轮实验设计的影响

| 发现 | 设计修正 |
|---|---|
| 故障绑定节点 ID | 若需测试"所有验证必败"场景，须将 fault 注入到所有验证节点 ID（包括拆分后的） |
| 拆分不继承故障 | 下一轮应增加一个"故障继承"对照臂：拆分子节点也注入故障，验证 Z 是否仍有效 |
| 合并合同故障 | 任务选择须确保验证节点确实消费异类输入（非同类） |
| 跨来源检查在 report | 不需要额外机制——report 合同已覆盖 |
| 成本完整 | 现有 Meter + 去重机制可靠 |
