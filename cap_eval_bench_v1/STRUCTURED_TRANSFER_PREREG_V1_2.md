## 2. 问题 1：撤回 n9 SUPPORTED 条件（附数据依据）

### 2.1 冲突确认

V1.1 §2.2 同时写了"v3 已包含 n9 SUPPORTED"与"第四个 TP 条件是本轮新增"，二者矛盾。
**事实是后者**：v3 的定义（REVISED_SCORING_V2_FP_AUDIT.md）只有三项 TP 条件
（值在终端值中、在 n1 输出中、在 n1 窗口内）+ 值级去重 FP，**从未包含 n9 状态**。

### 2.2 为什么不建立 v3.1 而是撤回（零调用核查结果）

对 A 臂（V7）全部 4 个块的 n9 输出做了格式审计：

| 块 | n9 JSON 可解析 | 状态字段 |
|---|---|---|
| V7-B1 | ✓ | CONFIRMED 15 / CONFIRMED_SINGLE_SOURCE 8 / PARTIALLY_VERIFIED 2 / UNKNOWN 2 |
| V7-B2 | **✗ 不可解析** | — |
| V7-B3 | **✗ 不可解析** | — |
| V7-B4 | ✓ | 已确认 32 / UNKNOWN 7（**中文词表**） |

结论：把"n9 判 SUPPORTED"设为 TP 门槛会造成三重不公平：

1. **覆盖缺口**：A 臂 2/4 块的 n9 输出不是合法 JSON，状态根本取不到——
   这些块会无条件失去所有 TP，而 B 臂因新的 ID 列表格式必然可解析。
2. **词表不一致**：A 臂同一实验内混用 `CONFIRMED`、`CONFIRMED_SINGLE_SOURCE`、
   `PARTIALLY_VERIFIED`、`已确认` 四种正向标签，映射规则必然需要人为裁定，
   等于给 A 臂引入一个主观评分步骤。
3. **等价性无法建立**：A 臂 n9 的角色是"跨来源核验"（输入 A+B），
   B 臂 n9 的角色是"逐条证据支持判定"，两者语义不同，不能声称同一条件。

因此：**撤回该条件。v3 保持原定义，不新增版本。**
两臂使用**完全相同**的 TP 判定规则（三项条件），评分器代码单一实现、双臂共用。

### 2.3 P03 类语义风险如何仍然被挡住

撤回后需回答：申辩语境/否定语境的事实会不会被误计 TP？**已有机制足以挡住**，
零调用复核给出确定性依据：

- TP 的前提是"值在**本轮 n1 输出**中"。P03（市场禁入）从未被任何 n1 提取
  （V6/V7/V8-2 十次运行全部未提取），因此它不可能进入 n1 输出 → 不满足溯源条件 → 不计 TP。
- 同理 P04（责令改正）、A02 等窗外事实。
- 十次历史运行的 v2.2/v3 重算中，P01–P04 均被标为 UNSUPPORTED_PROVENANCE 或未命中，
  无一计为 TP。**规则已经生效，无需再加门槛。**

### 2.4 降级为诊断指标（记录但不参与判定）

新增报告项 `n9_semantic_agreement`：
- A 臂：n9 输出中该事实的状态（原样记录，含不可解析标记 `UNPARSEABLE`）
- B 臂：SUPPORTED / REJECTED / UNKNOWN
- 用途：解释性分析（例如"B 臂终端多出的事实是否都被 n9 认可"），
  **不进入 H1–H4，不影响 CONFIRMED 判定**。
- 若两臂不一致，只作讨论，不作结论——因为两臂 n9 任务本身不同构（见 §2.2 第 3 点）。

## 3. 问题 2：H2b 纳入确认性验收

修正后的判定公式（冻结）：

```
CONFIRMED   = H1 ∧ H2 ∧ H2b ∧ H3 ∧ H4
CONDITIONAL = (H1 满足 ≥4/5 块) ∧ H3 ∧ (H2 回收 ≥2/3) ∧ H2b
NEGATIVE    = ¬H1 ∨ ¬H4 ∨ (H2 回收 ≤1/3) ∨ ¬H2b
INVALID     = 执行/预算异常（含 n1 输出非合法 JSON、调用超限）
```

H2 与 H2b 定义（H2b 不再是"辅助"）：

| 假设 | 事实 | 判据 |
|---|---|---|
| H2 恢复 | A03、A09、A01 | 在 `extracted=true` 的块中，B 臂终端出现率 ≥4/5，且 `extracted` 块数 ≥3 |
| **H2b 非回归** | E01、D03、D06 | 在 `extracted=true` 的块中，B 臂终端出现率 ≥4/5；A 臂同块结果并列报告 |

归因纪律不变：本块 n1 未提取 → 该块不计入分母；`extracted` 块 <3 → 标"样本不足"，不据此判通过。

## 4. 问题 3：n10 输出 Token 与 max_tokens 一致性

### 4.1 核查结果

| 项 | 数值 | 来源 |
|---|---|---|
| V7 实际 n10 `max_tokens` | **2,000** | 账本逐条实测（V6 时代为 768） |
| V7 n10 实际输出 | 1,673 / 1,905 / **2,000（截断）** / 1,713 | 4 个完整块 |
| V7 n10 均值 | 1,823 | — |
| V1.1 预算中的 2,125 | **估算值，且超过 2,000 上限 → 错误** | 已废止 |

### 4.2 修正

1. **B 臂 n10 输出估算改为 2,000（封顶口径）**，不再使用 2,125。
2. **两臂 max_tokens 逐节点完全一致**（冻结，不得因臂而异）：

| 节点 | n1 | n2 | n3 | n4 | n5 | n6 | n7 | n8 | n9 | n10 |
|---|---|---|---|---|---|---|---|---|---|---|
| max_tokens | 4000 | 768 | 768 | 768 | 768 | 768 | 768 | 768 | 2000 | 2000 |

3. **B 臂 n10 仍可能在 2,000 处截断**（它要报告的事实更多：最多 14 条 vs A 臂 11 条）。
   这是**结果的一部分**，不是缺陷：结构化传递必须在与对照臂**相同的输出预算**内完成，
   否则又会引入 V6→V7 的"容量耦合"混杂。截断必须记录并报告。

### 4.3 附带发现（重要，写入实验记录）

A 臂本身长期在容量边界运行（V7 四个完整块）：

| 节点 | 截断情况 |
|---|---|
| n2 | **4/4 块全部截断**（768） |
| n7 | 1/4 块截断（768） |
| n9 | **2/4 块截断**（2,000） |
| n10 | 1/4 块截断（2,000） |

含义：V7 基线的 n2 在每一块都被截断——中间管道的信息通道本身就是满的。
B 臂的 n2/n3/n4/n6/n9 输出为 ID 列表，通常远小于上限，
**其"不截断"是架构属性而非额外优化**；但因 max_tokens 相同，不构成容量混杂。
此项须在结论中如实说明：A 臂的截断是造成信息丢失的直接机制之一。

## 5. 其余设计（V1.1 已批准部分，原样保留）

- **唯一实验变量**：字符截断 `n1_output[:3000]` ↔ 结构化事实库（含确定性定位与 ID 引用）。

  `UNVERIFIABLE_ABSENT`；三态**均不自动计入 TP**。

  `provenance_status`、`spans`、`quote`（pad=10）；位置只在 n9 下发。
- **H2 归因**：逐块记录 `extracted` / `A_terminal` / `B_terminal`。

- **冻结条件**：同一份 n1 输出及 SHA256、同一模型、同一输入文档、同一 DAG 拓扑、
