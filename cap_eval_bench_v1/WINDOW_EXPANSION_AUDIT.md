## 任务 2：n1 输出容量

实测（V9 + V1.2 共 10 次 n1 调用，4000 窗口）：

| 事实库规模 | n1 输出 token | tok/fact |
|---|---|---|
| 46 | 2,872 | 62.4 |
| 49 (中位) | ~3,100 | ~63 |
| 54 | 3,153 | 58.4 |
| 61 | 3,321 | 54.4 |

线性拟合：**output_tokens ≈ 2,431 + 14.9 × facts**（R² 高，斜率随规模递减）。

| 预计事实数 | 预计 n1 输出 | 与 max_tokens=4000 |
|---|---|---|
| 75 | 3,546 | 余量 11% |
| 85 | 3,695 | 余量 8% |
| **98（8000 窗口密度外推）** | **3,891** | **余量 2.7%** |
| 110 | 4,067 | **超出 67** |

**结论**：n1 在 8000 窗口下**大概率刚好不截断，但没有安全边际**。
密度按实测 12.2 facts/1000 字符外推 → 约 **98 条事实**。任何一次输出偏长即触发截断，
而 n1 截断会让 JSON 不完整 → 下游事实库构建失败（V8-2 的同类风险）。

**不允许改 max_tokens 的前提下，n1 是"可用但脆弱"的约束，不是硬阻塞。**

## 任务 3：下游结构化传递容量（本轮的真正瓶颈）

### 3.1 输入规模（可承受）

| 节点 | 实测系数（4000 窗口） | 8000 窗口估算 |
|---|---|---|
| n9 输入 | 62.7 tok/事实 + ~200 | 98 × 62.7 + 200 ≈ **6,350**（无上限约束） |
| n9 输出 | ID 列表，47→282 tok | 98 → ~590 tok（cap 2000，安全） |
| n10 输入 | ~27.5 tok/事实 + 250 | 98 × 27.5 + 250 ≈ **2,945**（无上限约束） |

### 3.2 n10 输出：**已在当前规模附近失效**

| 观测 | fed 事实数 | n10 输出 token | 终端 TP |
|---|---|---|---|
| V1.2 各块（强模型） | 45–50 | 744–985 | **14** |
| V9 U-F B2 | 53 | — | **14** |
| **V9 U-F B4** | **54** | **2,706（未截断）** | **8 —— 六条日期全丢** |

**机制（V9 已观测）**：事实数上升 → 报告篇幅被实体与金额占满 → **日期整类被挤出**。
这不是 token 截断（B4 是 end_turn），而是**内容竞争**：模型在有限篇幅内按自己的优先级取舍。

**外推到 98 条事实**：n10 输出 token 线性外推约 **1,912**（cap 2000，余量 4%），
但**内容竞争会远早于 token 上限发生**——54 条时已经整类丢日期。
**结论：n10 的报告组织方式必须改（分类型分区输出 / 分节多次生成 / 或提高输出上限），
否则扩窗必然重演 B4 的失败。**

### 3.3 是否出现新的容量级联

**是。** 与 V6 的级联同族，但这次发生在**提示词事实量 → 报告篇幅**之间：
窗口翻倍 → 事实翻倍 → n10 篇幅竞争 → 类型级丢失。
且新增事实集中在 7244–7960 这一狭窄的处罚决定段落，**金额与处罚同类竞争**最激烈。

## 任务 5：当前 4000 窗口的实际质量天花板

- **理论天花板 14/22 = 0.636 Recall**（窗口内可达且语境有效的全部事实）。
- **实测已达 14/22**（V1.2 与 V9 所有臂）：**当前配置已 100% 打满窗口天花板**。
- 因此 V9 看不到模型差异是**必然的**：两个模型都能提取同一组窗口内事实，
  终端差异被天花板压平。这不是模型问题，是任务容量问题。
- Q_F1 天花板 = 2×1.0×0.636/(1.636) = **0.778**（实测 0.7778，完全吻合）。

## 任务 6–7：可执行性判断与最小配对预注册草案

**判定：CONDITIONAL**（不是 GO，也不是 NO-GO）

- 有 7 条新增有效事实 → 天花板可从 14 升到 21（+50%）。
- 但 n10 的报告容量在 **54 条事实**时已实测失效（B4 整类丢日期）；
  8000 窗口预计产生 ~98 条事实，**远超该阈值**。
- n1 输出容量"刚好够用"（余量 2.7%），无安全边际。

### 最小配对实验草案（**待操作员另行授权，本次不执行**）

- **自变量**：n1 输入窗口 4000 → 8000（唯一变量）。
- **必须先解决的伴随变更（否则实验无意义）**：n10 输出组织方式。三选一：
  1. n10 分类型分节生成（日期/金额/处罚/主体各一次调用）——增加 3 次调用/块；
  2. n10 max_tokens 2000 → 4000（改变容量契约，需声明为新变量）；
  3. 保留单次输出但强化"必须覆盖全部 fact_id"的指令 —— 最便宜、最不确定。
- **臂**：W4（4000，现有基线，零成本复用）vs W8（8000）。
- **块**：5 配对块（共享 n1 的原则改为共享文档，n1 各跑一次）。
- **主要判据**：
  - H-W1：W8 的 TP 中位 ≥18（回收 D07/D08/A02/A08/P01/P02/P04 中至少 4 条）；
  - H-W2：Precision 不劣于 W4（≥85%）；
  - H-W3：**日期类不得整类丢失**（V9 B4 的失败模式不得复现）——这是本草案新增的硬约束；
  - H-W4：n1 `stop_reason != max_tokens`（截断即 INVALID）。
- **预算**：约 60–80 次调用、≈230K token（两个资源包内）。
