# RQ1 V1.7 收益传播与 Oracle 对照（零调用）

## 1. 局部→终端的分解

`ΔQ_term ≈ Σ_nodes w_node × Δnode × propagation_node − cost/latency penalty`

- `w_node`：节点输出在终端唯一槽位中的权重（E04 35/100，E05 16，E06 17，E07 17，E08 15）。
- `propagation_node`：节点错误被下游放大/吸收的系数。
- 本模拟（synthetic）：局部 Δ=0.20 → 终端 ΔQ≈0.114；Δ=0.15 → 0.086；Δ=0.10 → 0.057。约 57% 的局部优势到达终端；上游 up=0.85 再降约 10–20%。

## 2. 关键节点

| 节点类型 | 终端作用 | 误差风险 | 是否值得高能力模型 |
|---|---|---|---|
| extract | 提供上游事实 | 遗漏/错值被下游放大 | 是，但需看证据分散 |
| timeline | 事件顺序 | 顺序错误改变结论 | 是（复杂时间关系） |
| merge | 跨文档合并 | 冲突未处理会放大 | 是（关键） |
| reason | 计算/推断 | 前提错误导致连锁 | 是（若可验证） |
| verification | 交叉核对 | 漏检导致错误进入报告 | 是（关键） |
| report | 终端汇合 | 综合错误直接损失 TP | 是，但边际收益取决于上游质量 |

**假设**：merge/verification 是误差放大的关键位置；extract 是上游质量的关键；report 的收益受上游限制。V1.7 要用真实实验检验，不能预设。

## 3. 机制问题

1. 哪些节点的质量提升能传递到终端？
2. 哪些节点是误差放大位置？
3. 哪些节点值得高能力模型，哪些是浪费？
4. 互补是否随 DAG 深度/分支变化？
5. 终端增益能否覆盖额外调用/时延？

## 4. Oracle Matching

- 在独立测试集上，对每个节点事后选择真实表现更好的模型，计算终端 Q 上限。
- 若 Oracle 无明显优势 → 模型池缺乏足够互补，节点级匹配无意义。
- 若 Oracle 有明显优势而实际策略达不到 → 问题在能力预测/调度，不在模型池。
- 限制：只用于测试集事后分析；不参与训练、选择、部署；不进入确认性策略比较。

## 5. 判据

- 机制成立：局部 Δ 与终端 ΔQ 同向，且关键节点的传播系数显著大于非关键节点。
- 策略成立：实际策略的 ΔQ_term 接近 Oracle 的一定比例（如 ≥50%），且 C/L/可靠性达标。
- 若局部提升但终端不提升 → 传播失败，不能归因于“模型互补”。
