# STAGE_D 终局执行器 Token 上限核算（第三阶段，零调用）

**依据**：完整 192 块 Mock dry-run 的 1,451 次调用记录（`runs_final_dryrun/`）；输入按字符计，输出按各层 `MAXTOK` 上限计。  
**约束**：零真实调用，无真实 tokenizer/API 计量；精确 token 校准 **BLOCKED**。

## 观测值

| 项 | 数值 |
|---|---|
| 调用数 | 1,451 |
| 输入字符数（Mock） | 2,213,618 |
| 输出字符数（Mock） | 209,935 |
| 观测 in+out（字符） | 2,423,553 |
| 每调用输入字符均值 | ≈ 1,526 |
| 输出上限（各层） | E=2,000 / J1=3,000 / J2=4,000 / SINK=4,000 |

## 保守上界

按“每调用 输入字符 + 该层输出上限”逐调用求和：

```
Σ (in_chars + MAXTOK[node]) = 6,209,618
```

- **1 字符 = 1 token 口径**：6,209,618。
- **1 字符 = 2 token 保守口径**：输出上限部分固定为 4,000,000；输入 2,213,618×2 = 4,427,236；合计 **8,427,236**。
- 再加 10% 余量：**≈ 9,270,000**。

**建议 GO 的全局 token 上限：9,500,000**（覆盖 2 token/字符的保守输入口径 + 10% 余量）。该数字是**建议值**，不是已写入配置的硬限制；配置当前 `global.tokens = null`，dry-run 只记账不硬停。

## 限制（BLOCKED）

- 无真实 tokenizer：以上是字符代理上界，不是模型 tokenizer 的精确计数。
- 真实调用中 GLM/DS 的输入 token 可能低于 2×字符；9.5M 是保守上界，不追求贴边。
- 若操作员要求更紧的 token 硬顶，需在 GO 前用真实 tokenizer 做离线校准（仍需零 API 调用，但需本地 tokenizer 资产）；当前环境未提供，**BLOCKED**。
