# D3 根因定位报告（更新版 · 零调用 · 2026-11-05）

## 初步结论的修正

此前我将 D3 归因于"DEEPSEEK_API_KEY 未设"——该修复**部分正确**（API 调用确实通过了：240s 直连测试显示 8 次调用 / ¥0.0304 / 12,948 tokens），**但 E 类节点仍然全部 Failed**。

## 更新后的 D3 根因：两层问题

### 层 1（已修复）：DEEPSEEK_API_KEY 环境变量缺失

冻结执行器的 deepseek 路径需要 `DEEPSEEK_API_KEY` 环境变量（`transport.py:15`）。修复后 API 调用成功（直连测试 0.7s 返回）。

### 层 2（未修复）：E 类节点的 deepseek 响应未通过冻结执行器的输出校验

在 240s 直连测试（宽松截止期、正确密钥）中：

| 指标 | 值 |
|---|---|
| 状态 | INCOMPLETE_NO_RECOVERY |
| 全局预算消耗 | calls=8 / ¥0.0304 / 12,948 tokens |
| E1–E4 | **全部 Failed** |
| J1/J2/SINK/FMT | Ready（因 E 失败而不满足依赖） |
| 检测信号 | **4 个 D1=model_suspect**（所有 E 节点） |
| makespan | 142.6s |

**API 调用本身成功返回**（8 次调用、有 token 消耗），但 deepseek 的响应**未通过冻结执行器 D2 spec 的输出格式校验**（E 类节点要求 `positions` 字段、结构化 JSON），被标为 `model_suspect` 后 Failed。

**这不是密钥问题，是模型输出与冻结合同不兼容的问题**——可能需要提示词工程或格式适配层才能让 deepseek E 类节点通过校验。

## 对 54 次实验的影响

在 E 类节点校验问题修复之前，任何真实执行（无论截止期多宽松）都会得到 TP=0——因为 J/SINK/FMT 永远因 E 失败而不满足依赖。

**需要的修复不是环境变量，而是让 deepseek 的 E 类响应通过 D2 合同校验。** 这可能涉及：
1. 在冻结执行器外部包装 format_repair（D3 格式修复动作已存在于 Fixed/Proposed 臂中）
2. 或修改子进程中的模型→节点分配（让 E 类用 GLM 而非 deepseek）
3. 或两者结合

**这需要新设计决策，不能由我单方面选定**，因为涉及冻结合同的解读。
