# H1 在线恢复决策零调用回放报告（2026-11-05）

## 一、决策回放设计

**数据源**：Stage-3（8 事件 × 5 臂）+ JOINT（场景 A/B）= **10 个决策点**（全部为真实异常事件的已知多臂结果）。

**控制器**：基于异常类型词表的规则控制器（金盲，仅使用运行时可观测信号——异常分类）。

## 二、回放结果

| 指标 | 结果 | 判定 |
|---|---|---|
| 有收益恢复识别率（TP） | **3/10 = 30%** | 低 |
| 无效恢复误触发率（FP） | **6/10 = 60%** | **高——通过关键验收的反面** |
| 应恢复未恢复（FN） | 0/10 = 0% | ✓ |
| 正确不恢复（TN） | 1/10 = 10% | 低 |
| **是否全部异常都触发恢复？** | **否**（有 1 个 TN） | 通过最低标准 |

**控制器特异性仅 14.3%**——远低于"真正具备决策能力"的要求。60% 的恢复动作未产生质量增益（浪费了 6 次调用的成本与时延）。

## 四、核心发现

1. **控制器未通过关键验收**——虽然不是所有异常都触发恢复（有 1 个 TN），但 **60% 的恢复动作无效**（浪费成本），说明当前的异常类型→动作映射过于粗粒度。

2. **Z/UPSTREAM 是最强动作但不是万能**——在 A4（信息坍缩但源文本身质量差）和 A7（执行失败且新采样反而崩塌）上 Z/R 均无效。

3. **真正的决策困难在"何时停止"而非"何时行动"**——FN=0 说明控制器不会错过有收益的机会，但 FP=60% 说明它不能识别恢复徒劳的情况。

## 五、改进方向

当前控制器的信号仅为异常类型（6 类），缺乏：
- **证据质量信号**：源文档中金标值是否存在（金盲版本=verify 放行数/覆盖度）
- **历史恢复成功率**：同类型异常在同类任务上的历史恢复率
- **预算感知**：剩余调用/token 预算是否支持恢复

建议下一版控制器加入：
1. verify 放行数=0 → 跳过 SINK 级恢复（A4/A7 型）
2. 异常类型×任务类型的历史恢复率查表
3. 预算门限

## 六、结论

H1 决策回放的**诚实结论**：简单规则控制器的特异性不足（14.3%），但方向正确（FN=0、A10 正确 NONE）。改进需要更丰富的运行时信号，不是修改异常类型词表。这为 H2（联合优化）提供了明确的控制器改进方向。
