# RQ2 V1：反馈驱动动态调度 + 验证纠错 + 质量/成本/时延联合优化

**状态：方案设计 + Phase 0 零调用上界审计完成；未启动任何真实 API；192 次真实额度继续 HOLD。**
**本轮不宣称 70% 已达成；70% 是新增研发目标，不是对 R5 验收标准的追溯修改。**

## 0. 先纠正指标口径

R5 的 `GQ/GF/GR/JOINT` 是 **100 次独立切分的验收通过率**，不是模型回答准确率。终端 Q 是另一条轴：

| stable H1 .20、20% matched | R5 数值 | 含义 |
|---|---:|---|
| Static 终端 Q | 45.48% | 统一 DS 基线 |
| MGC 终端 Q | 52.99% | 可部署 MGC 的切分均值（人口层 53.29%） |
| Node-Type 终端 Q | 55.89% | 成本/时延超限，不可部署 |
| GQ | 46% | 100 个切分中达到 MVS 终端增益的比例 |
| GF | 79% | 关键事实净收益检验通过的比例 |
| GR | 99% | 成本/时延/可靠性约束通过的比例 |
| JOINT | 42% | 同一切分同时满足 GQ∧GF∧GR 的比例 |

因此：

- “JOINT 42%” ≠ “回答准确率 42%”；它表示 42/100 个切分同时通过三项验收。
- MGC 的终端 Q 已经从 45.48% 提到 52.99%（+7.51pp），但 **52.99% 是绝对终端 Q，GQ 46% 是相对增益的通过率**；两者不能混用。
- 70% 目标至少要拆成两个问题：**GQ/GF/GR/JOINT 的 70% 通过率**，以及**终端 Q 是否要达到 70% 绝对值**。后者是更强的目标，见 §2.3。

### 1.1 三个直接结论

1. **静态 MGC 的 42% JOINT 远低于任务级分配上界 97.5%（stable .20、20% matched）**。R5 的 128 静态搜索不是“空间里没有质量”，而是“一个固定分配无法按任务适配”。这就是 RQ2 动态调度的价值所在。
2. **70% 的 JOINT 不是所有预算/情景都能靠分配达到**：10% 上界 60.3%，15% 上界 66.5%，20% strict 上界 67.6%；stable .15 strict 只有 29.1%，mixed 16.4%，stress 4.9%–54.3%。在这些区间，单纯动态换模不够，必须引入验证/纠错改变事实结果。
3. **若“70%”指终端 Q 绝对值，则在当前 128 分配空间内不可能**：stable .20 的无约束 per-task oracle 也只有 **57.68%**（Node-Type 55.89%）。70% 终端 Q 必须靠验证/修复提高事实 TP/定位/支持，而不是只换模型。

## 2. RQ2 的研究问题与目标

### 2.1 研究问题

- **RQ2-1（反馈换模）**：在相同成本/时延约束下，利用上游实际输出质量动态决定下游模型，能捕获多少 per-task oracle 的差距？
- **RQ2-2（验证纠错）**：独立验证 + 局部修复能否把关键事实 FP/FN/UNKNOWN 转为 TP，并在预算/关键路径内提高 GQ/GF/JOINT？
- **RQ2-3（联合优化）**：把换模、验证、局部恢复、关键路径 slack 放入同一个动作选择器，能否在 10/15/20% 预算和 strict 10% Makespan 下同时提高三项？
- **RQ2-4（边界）**：mixed 与压力情景下，增益是否仍成立；哪些目标在哪些 regime 物理上不可达？

### 2.2 新增目标（不作为 R5 追溯标准）

| 指标 | RQ2 目标 | 说明 |
|---|---:|---|
| GQ | ≥70% | 切分通过率 |
| GF | ≥70% | 切分通过率 |
| GR | ≥95% | 切分通过率 |
| JOINT | ≥70% | 切分通过率 |
| 成本 | ≤对应预算（10/15/20%） | 不增加预算 |
| Makespan | strict 1.10×Static | 原 10% 约束 |
| mixed/压力 | 单独报告 | 不合并、不藏负结果 |
| 终端 Q | 单独报告 | **与 70% 通过率不是同一指标**；若要求 Q≥70%，需另立目标 |

### 2.3 目标可行性（来自 Phase 0 上界）

- **20% matched、stable .20/.15**：上界 JOINT 97.5%/74.9%，70% 目标原则可达；F-AR/J-MO 是主战场。
- **20% strict、stable .20**：上界 67.6%，70% 目标在分配层面刚好不可达；必须靠 V-CR 补 2–3pp。
- **10%/15%**：上界 60.3%/66.5%，70% 不可由分配达到；V-CR 是硬需求。
- **mixed**：GF 上界仅 23.1%，JOINT 16.4%；关键事实验证/纠错是主瓶颈，不是 Q。
- **upstream/parse/up+parse**：20% matched 上界 54.3%/33.8%/21.4%；目标 70 在这些 regime 不现实，必须如实报告为负结果，除非 V-CR 大幅改变事实结果。
- **终端 Q 70%**：当前 128 空间无约束上界 57.68%，不可能只靠分配/换模；若坚持 Q≥70%，RQ2 的核心必须是验证/修复，而不是调度。

## 3. 三个机制

### 3.1 F-AR：反馈驱动模型重分配（不增加模型节点总数）

- 执行顺序按 DAG 拓扑；每个节点执行后立即得到事实结果与父节点 q（TP 比例）。
- 维护成本预算与 strict 时延预算；把 GLM 视为有限“token”（10/15% 最多 1 个，20% 最多 2 个；按 Static 成本算）。
- 决策函数只用**已观测信号**（父节点 q、节点类型、是否关键事实、report gate 风险、剩余预算/slack），不使用测试标签。
- 策略在训练集上学习阈值/小树；测试集只评估。
- 目标：捕获 per-task oracle 的一部分；上界见 §1。

### 3.2 V-CR：独立验证与局部纠错（不是“再加一个执行节点”）

- 不改变 7 节点 DAG；验证是对已执行事实的**动作**，可以复用 v 节点，也可以是一次独立校验 pass。
- 验证器输出“可疑/不可疑”信号；只对可疑事实做局部修复（重执行该事实/该节点，可换模型）。
- 关键参数（pilot 前冻结，不得看测试后调）：
  - 验证敏感度/特异度（GLM/DS 两档）；
  - 修复成功率（GLM/DS 两档）；
  - 每次修复的成本/时延（相对一个节点）；
  - 最大修复次数；关键事实优先、report gate 优先。
- 修复必须计入成本与 Makespan；不得凭空增加预算或突破 strict 10%。
- 目标：把 critical FP/FN/UNKNOWN 转 TP，提升 GF/GQ；在 mixed 下这是主机制。

### 3.3 J-MO：质量—成本—时延联合动作选择

- 候选动作：换模、验证、修复、跳过（不执行不必要修复）。
- 打分：预期终端增益 /（增量成本 + λ·关键路径时延）；优先使用 slack，避免在关键路径上引入不可逆时延。
- 约束：成本 cap、strict 1.10 makespan、解析/合同非劣；动作前做可行性检查。
- 与 R5 CPA 的区别：CPA 只做静态分配；J-MO 在执行中根据反馈选择动作，且可以放弃低价值修复。

## 4. 实验协议

### 4.1 情景与预算

沿用 R5 的 7 情景：H0、stable .15/.20、mixed、upstream、parse、up+parse。预算 10/15/20%；**strict 1.10 Makespan 为主**，matched 作为敏感性；MVS、终端评分、DAG、可靠性、价格/时延全部冻结。

### 4.2 对照

- R5 Static、MGC、CPA、Budget-Con、Node-Type（历史结果，不重跑）。
- RQ2 消融：F-AR only、V-CR only、F-AR+V-CR、J-MO。
- 上界：per-task constrained oracle（不可部署，Phase 0）；R5 Constrained Oracle（分配层）。
- 所有对照同任务、同 CRN、同预算/时延。

### 4.3 统计

- 100 次独立切分起步；通过 pilot 后再扩到 200 次/32+32。
- GQ/GF/GR/JOINT 为切分通过率；终端 Q 单独报告均值/CI。
- GF 用预注册精确符号翻转；GQ/GR 不变。
- mixed/压力情景单独报告，不合并成“平均成功”。

### 4.4 人员/资源

- 全部本地零调用；不消耗 192 额度；不调用 GLM/DeepSeek API；不启动真实 executor。

### Phase 0（已完成）

R5 指标纠正 + per-task 分配上界审计；结论见 §1。**只使用已有数据，零新调用。**

- 关键问题：F-AR 捕获了上界的多少？

- 先 stable .20 20s（上界 67.6%，目标需 V-CR 补 2–3pp）与 mixed（GF 上界 23.1%，验证是主瓶颈）。

### Phase 4：独立审计 + 报告

## 7. 边界与风险

- 上界是 **test-selected per-task oracle**，不可部署；F-AR 不会自动达到上界。
- 验证/修复参数是新假设；若参数过于乐观，70% 可能只是“假设的产物”。Phase 2 必须先做参数敏感度与机制合理性审计。
- mixed 的 GF 上界只有 23.1%，说明即使完美分配，关键事实检验也过不了；V-CR 必须真正改变事实结果，而不是只换模型。
- 70% 终端 Q 在当前 128 空间内不可达（上界 57.68%）；若坚持 Q≥70%，必须把 V-CR 作为核心，并重新审计其事实修复概率的合理性。
- 所有结论仅限合成机制；真实 GLM/DS 是否存在同样的类型互补，仍需真实模型验证，且需要新的明确授权。

**纪律：零真实 API；不消耗 192 额度；不改 R3/R4；不降低 MVS；不删任务；不把合成当真实；不凭 Monte Carlo 申请真实实验 GO。**

## 9. P0 终端质量解剖补充（2026-11-03）

- V-CR（保守，800 任务）Q=57.16%，损失 42.84pp；FN 29–30pp 是最大来源；定位 3.9–4.0pp、支持 4.6–4.7pp、report gate 1.3–2.4pp、FP 2.8–2.9pp。
- 节点损失集中在 reason `r`（10.05pp），其次 t/m/v/e1/e0/p；V-CR 的关键事实优先策略改善了 v/p，但 r 仍是 34.7%。
- 上界：只修事实 59.53%、只修定位/支持 60.72/61.80%、定位+支持 65.70%；只有“事实+定位+支持”联合达到 97.62%（完美修复，非部署）。
- 上游 q=1 仅 +5.4–6.9pp（Node-Type 62.44%），单独不足。
- 下一步 P1 质量优先修复/消融：事实+证据联合、优先 r/t/p、上游恢复；保留 Static/MGC/Node-Type/V-CR 对照；H0/sham/factorial 审计。
- 详见 `RQ2_P0_TERMINAL_ANATOMY.md`、`RQ2_P0_AUDIT.json`。

## 10. JFR-P1 归因补充（2026-11-03）

- 联合成功率 40.7% 的根因：78.3% 待修坏事实是"事实+定位+支持三缺"（FN 事实的 loc/sup 机制性为 false），成功率钉死 .70³=.333；三阶段边际几乎相等（.716–.744），无单一短板。
- 容量：坏事实约 7.0/任务，触达 3.70，转换 1.50；70% 需 3.21 转换/任务。当前容量下需要每事实产出 0.87（单阶段成功率≈95%）；扩触达至 5.2 需 0.62（≈85%）；全覆盖需 0.46（≈77%）。
- 共享证据恢复目标池 1.02/任务（e0/e1/t 为主），完美修复上限 +7.9pp→65.2%，单独不到 70；价值主要在成本侧（当前预算把 1.14 个已标记真坏节点/任务挡在门外）。
- H0 增益更大的机制解释：H0 base 更差、坏事实更多（8.7 vs 7.0/任务），三阶段成功率两世界几乎相同；修复是模型无关的均匀纠错。归因修复方向=能力相关修复（用 GLM 重执行坏节点）。
- 详见 `JFR_P1_ATTRIBUTION.md`、`JFR_P1_ATTRIBUTION_AUDIT.json`。

## 11. P2-0 节点可重建性分析补充（2026-11-03）

- reason 失败档案：90.5% 任务有坏 r 事实；82.9% FN；57.3% 双坏；父 q 0.435。
- 重建产出（最优模型、新抽取期望）：m 0.86 / v 0.76 / e1 0.81 / e0 0.78 / t 0.69 / **r 仅 0.46（双坏同修 19.3%）** / p 0.40。r 对两模型都难。
- 成本/时延：GLM 重建 +0.143 > 20% 档余量 0.12（任何节点放不下）；DS 重建 +0.086 至多 1 个；事后重建时延 +18.4%～+42.1%（仅 p-DS 落 matched-20）；投机并行 GLM +6.1–10.5%（strict 可守）但成本同样被卡。
- 70% 的解析价格：完美检测 ≈2.2× 成本 → Q≈71.5%；sens .75 → Q≈65.0%；冻结 20% 预算内 ≈47.9%。
