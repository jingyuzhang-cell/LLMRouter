# RQ1 V1.8.2 Oracle 交叉拟合分析

## 1. 三个 Oracle 的 H0 与效应（V1.8.1 20k）

| Oracle | H0 | 局部 0.15 | 局部 0.20 |
|---|---|---|---|
| True（真实参数） | 0.0000 | +0.0855 | +0.1140 |
| Cross-fitted（训练选/测试评） | +0.0001 | +0.0851 | +0.1139 |
| Naive（测试取最大） | +0.1321 | +0.1476 | +0.1608 |

- Naive 的 H0 +0.132 是 max-of-noisy 选择偏差；不能作为“模型池互补”的证据。
- CF 在 H0 下为 +0.0001，与 True 接近；CF 是当前最可信的可实现上限估计。
- Naive 与 CF 的差（+0.13）是选择偏差，不是互补。

## 2. 训练任务数量对 CF 稳定性的影响（设计，未跑）

- 计划：训练 5/10/20 个任务；每节点模型在训练上选，测试评估；重复 20k；报告 CF 的均值/方差/CI 覆盖率。
- **本轮未完成**；不得用未跑结果声称 CF 稳定。
- 预期：训练任务少时，类型级均值噪声大，CF 的方差上升；需要 ≥10 个训练任务才可能稳定。

## 3. 方向不一致时的 Oracle

- 方向不一致时，True/CF/Naive 的终端收益也会下降；CF 的类型选择无法捕捉任务级方向。
- 这解释“Oracle 有收益而 Router 没有”：不是模型池无互补，而是预测/选择无法识别任务级方向。
- 需要任务条件化/路由器；但简单 Task-Conditioned 规则在 V1.8.1 中也未恢复收益（−0.012）。

## 4. 收益损失分解

`模型池潜在互补（True Oracle − Best）`
→ `预测误差（True Oracle − CF）`
→ `选择误差（CF − 实际 Router）`
→ `上游传播损失（节点级 → 终端）`
→ `解析失败损失`
→ `终端实际收益`。

- V1.8.2 只完成了 True/CF/Naive 的 H0/效应对比；训练规模、Router 差距、上游/解析分解需在后续零调用中补齐。
- 不能把 Naive 减去常数当无偏；CF 的不确定性要进 CI。

## 5. 结论

- 模型池在 synthetic 中有互补（True +0.0855），但 Naive 的 +0.1476 高估了它。
- CF 的 +0.0851 是当前最可信的可实现上限；实际 Router 的收益（V1.8.1 Node-Type +0.0851）在理想 H1 下接近 CF，但在方向不一致时降到 +0.012。
- 因此“能否利用互补”取决于预测/选择，而不是模型池本身。
