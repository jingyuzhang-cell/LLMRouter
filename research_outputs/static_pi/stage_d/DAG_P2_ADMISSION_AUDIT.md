# DAG-P2 零调用准入审计（五项 · 2026-11-05）

## 审计结论：**有条件通过——存在一个关键设计缺口**

## 一、P1 优化器是否真正产生结构变化？

**源码**：`dag_optimizer.py`（299 行），支持 MERGE_NODES / SPLIT_NODE / REMOVE_EDGE / ADD_EDGE / REMOVE_NODE / ADD_NODE 六种操作。

**实测**：在 E04 参考 DAG（6 节点 6 边）上运行 → **0 变更**。参考 DAG 已是优化器认为的最优结构。

**判定**：✓ 优化器功能正常（23/23 测试通过有历史记录），但 **E04 参考 DAG 无优化空间**——不能在此任务上验证"结构优化的收益"，因为 Raw = Optimized = Reference。

## 二、E04 三种结构的可比性

| 结构 | 节点 | 边 | 来源 |
|---|---|---|---|
| Reference | 6 | 6 | 人工冻结 |
| Optimized | **6** | **6** | 优化器输出=零变更 |
| Raw（初始） | ? | ? | **不存在**——无 LLM 生成的初始 DAG |

**关键缺口**：P2 设计要求 Raw → Optimized → Reference 三组对照，但：
1. **Raw DAG 不存在**——需要先有一个"未优化的初始 DAG"作为起点
2. **优化器对参考 DAG 无操作**——无法产生"优化前后"的差异

**要使 P2 可执行，必须先构造一个"有冗余/可优化的 Raw DAG"**。这不能人为制造——需要用 LLM 从任务描述自动生成一个真实的初始 DAG（可能包含冗余节点/边/依赖），然后让优化器对其优化。

## 三、是否存在真实的结构优化空间？

**历史审计结论**：
- r2fix diamond_8 / pilot typed DAG：**未发现可确认的冗余边**
- 舜天 DAG：**一条疑似重复依赖边（待实测）**

**当前判定**：⚠️ 在现有手工设计的 DAG 中，**结构优化空间很小**。优化器的主要价值可能在 LLM 自动生成的 DAG（可能包含冗余），而非人工精调的参考 DAG。

**这提示一个更根本的问题**：P2 实验应从"LLM 自动生成 DAG"开始，而非从"人工参考 DAG"开始。流程应为：

```
任务描述 → LLM 自动生成 Raw DAG（可能含冗余）
→ P1 优化器 → Optimized DAG
→ 与人工 Reference DAG 对比
```

## 四、三组能否共用同一执行环境和评价口径？

✓ 可以——`stage_d_executor.py` 已支持自定义 DAG 结构（nodes/edges/spec 均可配置）；TP/23 评价口径已冻结。

**前提**：三组 DAG 的节点 `kind` 和 `doc_refs` 必须兼容当前执行器的调度逻辑。

## 五、预算与预注册有效性

原 P2 规划（~50 次调用 / 50K tokens）为**旧版**，不构成本轮授权。

**新版预算估算**（假设 Raw DAG 需 LLM 生成）：
- LLM 生成 Raw DAG：1-2 次
- 三组 × 3 重复 × E04 型 DAG（~5-7 节点）：~45 次执行
- 总计：**~50 次 / ~80K tokens / ~¥0.50**

## 六、P2 实验的修订建议

**原设计**：Raw（已有）→ Optimized → Reference
**修订**：LLM 生成 Raw → P1 优化 → Optimized → Reference（人工冻结）

| 步骤 | 内容 | 调用 |
|---|---|---|
| 1 | LLM 从任务描述自动生成初始 DAG | 1-2 |
| 2 | 零调用运行 P1 优化器 → Optimized DAG | 0 |
| 3 | 三组（Raw/Optimized/Reference）× 3 重复执行 | ~45 |
| 4 | TP/C/L/DAG 结构/执行失败率 统一分析 | 0 |

**判据**：
- 主判据：Optimized vs Raw 的 C 或 L 改善（Q 非劣）
- 次级：Optimized vs Reference 的结构/质量差距
- DAG 结构指标：节点数/边数/关键路径长度变化
