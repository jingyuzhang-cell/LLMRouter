## 1. Z 的正式定义（替代 V2.2 §1.1）

### 1.1 定义

> **Z：基于 DAG 结构重构的任务重新分解机制。**
> 包括：节点拆分、依赖边调整，以及**与新子任务对应的必要输入/输出合同与提示词派生**。

**说明**：E 节点拆分必然带来子任务职责范围、子节点提示词、子节点输出 schema 与原节点执行次数的变化。
这些是**任务重新分解的必要组成部分**，不应被排除在 Z 之外——否则 Z 无法实现。

### 1.2 明确禁止（不属于 Z）

| 禁止项 | 理由 |
|---|---|
| 对**原节点**单纯增加提示词补丁（如 J1 加 RELAY_ADDENDUM、J2 加 DISAMBIG_ADDENDUM） | 不改变拓扑与任务分解 |
| 不改变 DAG 的提示词优化 | 同上 |
| 不改变任务分解的模型参数调整 | 属 π，不属 Z |

**操作性判据**：一个干预是 Z，当且仅当**存在拓扑差异**（节点集合或依赖边发生变化），
且每个新节点的合同/提示词是**为该新子任务派生**的（不是给旧节点打的补丁）。

### 1.3 实现的合法性断言（已在执行器中）

`v2/executor_v22.py::Z_split` 记录 `dag_version` 与 `edits[{op:'split', added:[...]}]`，
并在测试中断言：旧节点 `deleted=True`、合并节点继承旧出边、子节点继承旧入边、
无悬挂边、无环、原节点不再可调度。

## 3. S4′ 重新定义（回应"检测机制不明确"）

### 3.1 问题（您的判断正确）

`PURE` 校验的是**合同与格式**（fact_id 存在、值类型/格式），**不能发现"格式正确但事实错误"**。
若把 S4′ 定义为"语义错误"，则调度器根本不会被告知——模型输出错误事实，PURE 通过，无异常。

### 3.2 正式定义（可确定性检测）

> **S4′ 注入：SINK 输出在 L1 规范化之后仍违反冻结合同的确定性检查。**
> 检查项限定为三类：
> 1. **必需字段缺失**（如 `answers` 中某 `fact_id` 未出现）；
> 2. **字段类型不符合冻结 Schema**（如 `value` 为 null 或数组）；
> 3. **必需数组结构不完整**（如 `abstentions` 缺项）。
>
> L1 **只做规范化，绝不凭空补造事实**；规范化后仍不合规 → `fam=format_residual` → 触发策略。

- **检测点**：L1 之后；
- **记录**：`l1_fixed`（L1 是否修复成功）、`residual_violations`（具体项）；
- **Z**：不适用（无拓扑解法）；
- **π**：适用（换模重跑 SINK）；
- **统计**：S4′ **单独分析 π 的增量**，作为机制边界与负对照，**不得并入 Z 主效应/交互效应**。

### 3.3 语义错误研究（不在本轮）

若将来要研究"语义错误"，必须另行定义：
独立验证器（非 PURE）、证据依据、触发权限、误报率。
**不得把语义 Gold 直接当作运行时可用反馈。**

## 4. 故障持续性（勘误 V2.2 的 S1/S1b 注入方式）

### 4.1 冻结代码的现状（问题）

`d2_executor.corrupt_once` 是**一次性**的：

```python
if node == "E2" and self.scenario == "S1" and not getattr(self,"_s1_done",False):
    self._s1_done = True
    ... d.pop("positions", None)
```

→ R₀ 重跑拿到的是**干净输出**，Z 没有任何作用空间。
更糟的是：若注入器按**节点名**匹配，E2 拆成 `E2_pos`/`E2_rest` 后会**绕开故障**——
Z 会因为错误原因看起来有效。

### 4.2 选择：持续性、spec 级故障（预注册）

> **S1/S1b 的故障 = 初始 E 节点的 spec 本身过度负荷，导致 positions 系统性缺失。**

实现方式：初始 `E2`（或 `E1`）的 sys 为**不含 positions 指令**的版本；`detect` 每次都会报
`structure`（因为输出确实没有 positions）。
- **Retry-only**：用同一缺陷 spec 重跑 → 仍然缺失（故障持续）；
- **Z**：拆成 `E2_pos`（派生合同，只抽 positions）+ `E2_rest`（其余字段）→ 有恢复机会；
- 故障**不随节点改名而消失**，因为子任务的合同是从任务需求派生的，不是继承缺陷 spec。

### 4.3 预注册的实验问题（写进论文口径）

> 本实验测量的是：**在 E 节点抽取合同过度负荷（持续性、spec 级）导致字段系统性缺失时，
> 任务重新分解是否优于普通重执行。**
> 它**不是**"瞬态输出损坏下的结构修复"，也不是"任意抽取困难"的普遍结论。

## 5. 工程门禁（已实现并通过离线测试）

`v2/executor_v22.py` + `v2/test_v22_gates.py`（**零网络**）：

| 门禁 | 验证内容 | 结果 |
|---|---|---|
| **G1 DAG 版本一致性** | 旧节点 `deleted`、合并节点继承出边、子节点继承入边、无悬挂、无环、旧节点不可调度、`dag_version`/`edits` 可追溯 | **PASS** |
| **G2 π 作用域** | `U = active DAG 中尚未派发的模型节点`；Running/Completed/deleted/代码节点均不进入；实测 `U={E2_pos,E2_rest,SINK}`，scope 一致 | **PASS** |
| **G3 调用预算** | 最坏路径枚举 | **PASS 但零余量（见 §5.1）** |
| 故障持续性 | Retry-only 无法恢复、Z 可恢复 | **PASS** |
| 六臂对齐 | 四因子臂仅 Z、π 不同；Static 无 R₀ | **PASS** |
| 随机化 | 9 个区组（3 状态 × 3 重复）臂序全部不同 | **PASS** |

### 5.1 G3 暴露的公平性问题（必须修正）

最坏路径 = 7（基线）+1（Z 拆分）+5（R₀ 重跑拆分子节点 2 + 闭包 3）+1（一次传输重试）= **14**，
**恰好等于每执行上限 14，零余量**。若两个不同节点各触发一次传输重试 → 15 > 14，
**Z 臂会因预算耗尽而被迫 INCOMPLETE**，而 Retry-only 不会。

**修正建议：把每执行调用上限从 14 统一提高到 16（六臂一致）。**
这是**公平性修正**，不是处理差异——否则预算上限本身会制造"Z 更差"的伪结果。
