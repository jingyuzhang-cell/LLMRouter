# E4 授权额度突破事故报告（2026-10-14）

## 事故结论（先说数字）

本轮授权上限：**120 次调用 / 400,000 token / ¥1.00**。
实际消耗：**79 次调用 / 466,666+ token / ¥1.0393**（最终账本核验：79 calls、469,666 tokens、¥1.0393）。

- 调用数：79/120 ✅ 未超
- **Token：超出 69,666（+17.4%）❌**
- **现金：超出 ¥0.0393（+3.9%）❌**

这是对授权协议的实质违约，责任完全在执行侧（我），与模型行为、API 波动无关。逐笔流水见
`e4_ledger.jsonl`（79 行，含 run_id/ts/用量/费用，全程可审计）。

## 直接原因（技术链）

1. 09:0x v1 真实运行暴露截断级联（GLM/DS 输出上限过低 + KDX 证据窗 19K 字符远超预算假设），
   我调用 TaskStop 停止后台任务——**它只杀死了 shell 包装进程，python 子进程存活并继续执行
   v1 的运行清单**（st:B1、st:B2、st:B3p……），我未验证进程确实死亡，这是本次事故的根本操作失误。
2. 我归档 v1 结果、修改脚本（v2：缩减证据窗 8K、提高输出上限、砍掉非判别性臂），启动 v2。
3. **两个实验进程并行运行约 4 分钟**：各自持有独立 ExpMeter，各自只看到自己的部分视图，
   两者合并的真实消耗突破 token 与现金上限。它们还并发写同一个 e4_results.json（该文件以
   v2 的 3 个有效运行告终，v1 的写入被覆盖——账本未受影响，按 run_id 完整保留）。
4. 附带影响：双进程争抢 API 使单调用时延显著上升（B1 的 t1 单调用 27.7s），污染了本轮的
   时延测量（质量测量不受影响，账本逐调用记录可事后剔除）。

## 整改（已完成，零成本）

1. `e4_controlled_experiment.py` 增加 **OS 级排他锁**（fcntl.flock）：第二个实例立即拒绝启动
   并明确报错，杜绝同类并发双花。已验证：单实例正常、第二实例被拒。
2. 停止例程改为：停止后必须 `pgrep` 验证子进程死亡，才允许任何后续动作（本报告即执行记录）。
3. 计量器已改为**从既有账本续算**（含 v1 沉没成本），后续任何续跑都从真实剩余额度出发。
