# RETRIEVAL_IMPROVEMENT_RESULT — 零付费检索改进实验（2026-10-14，DEV阶段，KDX）

**一句话结论：同等 10K 预算下，任务驱动多查询重排序（RRF）与动态分支预算都没有提升证据覆盖
（1/4 vs 基线 2/4，反而丢分）；真正有效的杠杆是窗口大小——冻结的 50/50 分线检索在 20K 字即达
4/4 全覆盖。本结果为 DEV 阶段开发发现，必须在独立事件上验证，不得与冻结协议混称。**

数据：`retrieval_improvement_result.json`；代码：`retrieval_v3.py`（改进算法）、
`retrieval_improvement_experiment.py`（对照实验）。全程零模型调用；冻结基线代码与结果零改动。

## 发现一：同预算重排序改进为负结果（如实报告）

- RRF 融合（4 个任务子面：处罚/问询/造假/主体，全部来自冻结 TASK_TERMS 词表，零 Gold 依赖）
  在**每个窗口档都劣于单一 IDF 评分**：10K 下把含 RF1（60万元罚款）的高密度处罚认定块
  挤出上下文（1/4），20K 下仍丢 RF1。
- 机理：本事件的 T1 锚块集中在处罚决定书的高词密段落——"多面均衡"反而稀释了深命中文档的
  配额。多样性与深命中在此语料上互斥。
- 动态分支预算在 10K 下近似无效（两线质量份额 50.2%/49.8%，与 50/50 几乎相同）。

## 发现二：窗口扩展是当前规则下的有效杠杆

- 冻结 50/50 分线：10K=2/4 → 15K=3/4 → **20K=4/4（全部事实证据可达）** → 25K 维持 4/4。
- RF4（北京银行现金管理协议，全局单一评分第 54/200 位）在 20K 时经**线内排序**自然进入：
  问询线只有两份文档，线内配额下其包含引文的块排位足够靠前——无需语义检索、无需定向召回。
- 成本与时延（20K vs 10K，按实测锚点外推）：每 DAG 运行输入约 +6.7K token（6,703→13,405），
  DS 抽取节点现金约 +¥0.008/运行（非高峰价），抽取节点时延约 +4–5s（输入线性外推）。

## 发现三：开发过程中的一个实现教训（已修复）

邻居块"补充"最初实现为优先插队，导致沿单文档线性填充：文档多样性 5→2、覆盖 2/4→0/4。
已改为**排名填充后的剩余预算补充**。该教训写进 `retrieval_v3.py` 注释，防止复发。

## 反泄漏与防摘樱桃声明

- 检索构建只用任务文本词表、文档标题/元数据、正文；`retrieval_v3.py` 无任何文件 IO、
  不含参考事实文件名（与 v2 打包器同一隔离标准）。
- 未按 RF3/RF4 已知位置构造查询；未在事后按覆盖挑配置——RRF/动态预算为预注册变体，
  冻结基线窗口扩展是用户对照表的既定行；负结果如实保留。

## 边界与下一步（ DEV 标记）

1. "20K 全覆盖"是 KDX DEV 上的发现，已知缺失事实后开发/测量，**必须在独立事件（如 ST）
   上零付费复验**后才可作为协议候选；
2. 若采用 20K 窗口，四运行预算需重估：每运行输入约 13.4K+（10K 时约 6.7K），
  原 160K token 上限下四运行接近贴线，需用户重新核数授权；
3. RRF/动态预算判为 DEV 否定结果，不进入协议；
4. 已排队的 F7 四运行（冻结 10K 输入）未做任何改动，按原计划在非高峰窗执行。
