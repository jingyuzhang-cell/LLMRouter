# Stage 3 端到端资源包络零调用收口

## 1. 完整调用路径

唯一真实验收入口fresh_acceptance.main：冻结公开任务/独立评分文件检查 → ScopedBudget.bind_envelope（模型启动前）→ 来源哈希/模型加载/健康GET → tokenizer → PreparedExecutor.call → prepare_request → ScopedBudget.check_request → MeteredExecutor.call → ScopedBudget.reserve → HTTP dispatch → Budget.settle/阶段结算。

InitialDAGGenerator.generate最多两个attempt：初次plan；若失败一次repair。每次合法装配后至多一次semantic_review，因此review最多2次。结构/合同/引用验证、确定性装配、固定回退构造均零调用。真实入口不执行固定回退。

TypedExecutor.run中非transformation节点通过同一个metered.call：facts抽取、expression推理、verify_expression/verify_value验证均为LLM请求；验证包含在最多5个LLM节点额度内，不额外重复加一次。calculate.v1通过exec_calc，零模型请求。事实溯源/表达式绑定/数值一致性检查均确定性零调用。一次recover_failed只重试失败目标；尚未运行的后继继续使用原node槽，已完成节点不重放，因此执行总上限5+1=6。恢复不能使用gold。score_final调用确定性score_v21，零模型请求。加载prepare=lambda和GET健康检查也不产生模型推理请求。

## 3. 开始前与逐请求准入

ResourceEnvelope.admit检查全部预定任务的阶段/题/全局最坏Token、请求数和名义墙钟包络。当前请求使用实际本地tokenizer输入计数+max_output最大预留。check_request再次保留本题尚未使用的所有阶段槽（包含可选修复/恢复）以及其他题全部未消耗槽；未确定失败用量保留全额，与实际已知用量共同占用charged。每阶段自身预算和执行槽独立，生成无法侵占执行资源。原reserve强制检查仍在，且再次执行包络检查；缓存不提供乐观预算抵扣。

阶段明确结束后release_unused只释放未来槽，已发请求/失败账本绝不回滚。标记后的阶段不能再调用。所有大小/阶段/题/全局/时间拒绝有独立JSONL日志。

单HTTP绝对上限30秒，防止socket空闲超时在慢速返回下不断延长；无重试。模型启动300秒、两题最坏20请求×30秒、清理30秒，名义合计930秒<1200。入口墙钟从main开始计时；全局SIGALRM在1170秒触发StopRun并保留30秒清理，包含模型哈希扫描、加载、健康检查、tokenization、实验。绝对请求定时器恢复原全局剩余时间，不重新启动20分钟。

## 4. 两轮历史重放

HISTORICAL_REPLAY.json包含逐请求原始哈希/预留/用量及反事实准入。第一轮4请求/5455 Token，第二轮4请求/7652 Token；8次均input_tokens+max_output正确。全部有合法用量返回，真实未知用量留存为0；未知失败保留通过Stub测试，不冒充历史发生过。

旧信封在新完整准入下两轮均应在第一调用之前拒绝（生成/执行最坏阶段及全局不足），因此新停止决策是启动前0调用，而不是沿用历史生成后停止。第二轮旧未派发修复预检2481+已耗3913=6394>6000，旧阻断正确。反事实新56000/阶段14000信封会允许这次预留；这不是实际派发，更不是修复、覆盖或执行成功。两轮均无生成借用执行预算的证据；原始账本内容哈希重放前后完全一致。

## 6. 保证及未能保证的风险

保证范围是符合输入输出长度边界的派发资源有界，违规请求拒绝、未知费用保留；不是任务必定完成、语义覆盖正确、输出JSON不截断或答案正确的保证。新生成图可能使执行Prompt超过2048，此时安全停止，不能宣称任何图均可执行。模板/schema与实际服务tokenizer若不一致、供应商返回不可信用量仍触发计量失败，并保留预留。

30秒会造成正常但较慢调用超时，应在新批准信封内真实验证；不根据历史质量数据调参。SIGALRM仅支持当前Linux主线程入口；OS不可中断I/O、进程被SIGKILL、GPU驱动故障等不能由Python证明按时清理，仍需外部监督。模型加载和本地计算没有成功完成时间保证，全球截止可以停止流程，不保证获得结果。Python无法证明服务端实际计算绝不会超过它自己报告/接受的max_tokens，计量界以既有服务API契约及验证为前提。
