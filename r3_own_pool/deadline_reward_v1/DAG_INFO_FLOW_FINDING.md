# 根因分析：DAG 信息流设计缺陷导致恢复策略无价值

## 发现

在 CT03、CT10、CT10-FJSON 三次实验中，无论何种故障类型（截断/垃圾）
和 DAG 结构（钻石/链式），恢复策略均不改善终端质量。

**根因**：`TrueDAGChain.build_prompt()` 在每个节点的提示词中直接包含
文档全文。当文档对所有节点可见时，节点输出不携带下游需要的独有信息
——DAG 是处理管线，不是信息依赖链。

## 当前信息流 vs 修复后信息流

```
当前（有缺陷）:
  extraction: [文档全文] → 提取事实
  reasoning:  [上游输出 + 文档全文] → 推理     ← 问题在这里
  verification: [上游输出 + 文档全文] → 核查    ← 问题在这里

修复后（信息诚实）:
  extraction: [文档全文] → 提取事实             ← 唯一信息入口
  reasoning:  [仅上游输出] → 推理                ← 依赖上游
  verification: [仅上游输出] → 核查              ← 依赖上游
```

## 预期效果

修复后，恢复策略将首次具有可测量的价值：

| 臂 | n0 输出 | n1-n7 接收 | terminal_q | 预期 |
|---|---|---|---|---|
| D0 | 垃圾 | 仅垃圾（无文档） | **~0.000** | 质量崩塌 |
| D2 | 修复→正确 | 正确事实 | **~0.500** | 质量恢复 |

## 实现变更

- `exp4b_infrastructure.py` 的 `build_prompt()` 方法：
  - extraction 节点保留 `doc_text`
  - reasoning/verification 节点移除 `doc_text`，仅保留上游输出
- `terminal_eval.py` 无需变更
- 评分参考无需变更

## 风险

reasoning 节点仅接收上游提取输出（无完整文档上下文）时，可能产出
质量较低的推理。**这正是设计意图**——创造真实的信息依赖。
