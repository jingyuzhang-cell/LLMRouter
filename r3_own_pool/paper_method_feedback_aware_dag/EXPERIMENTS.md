# 5 Experiments

本章围绕 Feedback-aware Adaptive DAG Routing 的四个目标展开实验：提高复杂任务处理质量，在可比质量下减少推理开销，增强异常恢复能力，以及提高多轮追问中的历史计算复用效率。实验依次考察模型能力异构性、冻结节点路由、反馈学习、失败驱动调整、图复用和多目标选择，最后通过三臂综合回放分析模块组合后的行为。为保持证据口径一致，本章区分真实模型调用、基于已采集回答的顺序回放，以及由组件统计量驱动的模拟；不同层级的结果分别解释，不将模拟性能等同于部署系统的实际性能。

## 5.1 Experimental Setup

实验的总体目的是检验任务节点能否提供比完整查询更有效的模型选择粒度，并进一步分析执行反馈与图结构调整是否能够补充静态选择。节点路由采用独立确认设置，后续机制实验复用该面板或其选定子集。因此，独立确认支持冻结路由器的泛化判断，而后续开发性试验主要用于机制分析，不能视为又一次未接触数据上的独立确认。

主要数据来自 MultiHiertt。节点路由开发面板包含 201 个任务、372 个节点；独立确认从有标签的 train split 中审计未参与当前开发的任务，再按固定规则选取 100 个复杂任务。官方 test split 缺少现有评分所需的答案、程序与节点证据，因此没有将其作为有监督确认集。审计排除了已知任务标识和标准化问题重复项，其结论限定于已检查的工作区使用记录，不涉及基础模型预训练数据。确认集包含 193 个 extraction、100 个 reasoning、200 个 verification 节点，合计 493 个主要节点；另有 4 个 transformation 节点，仅作探索性记录。

模型池固定为 medium、large 和 coder，分别对应 Qwen2.5-7B-Instruct、Qwen2.5-14B-Instruct-GPTQ-Int8 和 Qwen2.5-Coder-7B-Instruct。R1 不进入节点路由实验。问题表示来自冻结 GTE-Qwen2-7B-instruct 编码器；节点路由在问题表示上拼接节点类型和问题字符长度的对数，并对各模型分别使用 Ridge 预测质量，正则强度固定为 1。成本与延迟先验来自开发数据均值。确认前封存模型参数、特征和效用权重，确认数据只用于推断与评价。

Quality 定义为相应节点评分的平均值。抽取依据目标事实是否正确，推理依据表达式执行值是否与标准答案匹配，验证依据接受或拒绝判定是否正确。Task Success Rate 在综合回放中定义为最终 reasoning 节点正确的任务比例，不要求所有中间节点同时正确，因此与完整在线 DAG 成功率不同。Token Cost 统计输入与输出 tokens，作为推理资源代理，不等同于货币费用。Latency 在静态确认中为去重调用服务时间的任务内累计值，包含实际调用耗时，但并非独立部署条件下的端到端墙钟时延。

Recovery 区分两种含义：失败恢复率为成功修复数除以相应失败样本数；GAP Recovery 为方法相对基线的质量增量除以 Oracle 与该基线的质量差。后者随基线定义而变化，不能直接解释为修复了多少失败任务。Reuse Rate 表示追问计算中复用的逻辑节点比例，Call Reduction 和 Token Reduction 则比较相应调用数与 token 消耗。共享调用必须去重，逻辑节点数不必等于物理请求数。

统计比较以同一任务为配对单位，保留任务内部节点依赖。静态确认的置信区间来自任务聚类 bootstrap；没有重复运行或置信区间的机制结果仅报告观测值。尤其是条件节点面板为推理和验证提供标准事实或扰动事实，减少了上游错误的影响，因此它首先验证给定输入下的选择能力。上述设置使后续各节能够分别回答“选择是否有效”“反馈是否有帮助”和“完整执行是否已被验证”，而不会将三个问题混为一谈。

为便于跨表阅读，质量差统一用百分点（pp）表示，资源降幅采用“基线减方法后除以基线”的相对比例。例如，质量增加 0.069 对应 6.9 pp，而不是相对提高 6.9%。表中“未记录”表示现有结果没有相应可比指标，不按零值处理。一次性节点采集的总请求数用于说明数据收集规模，策略执行成本则只统计该策略选择的请求，两者不能混用。上述区分也适用于后续组件试验：收集所有候选回答的离线投入，不等于路由器实际部署时每题都调用所有模型；同样，利用完整面板计算的事后 Oracle 也不是可执行基线。

## 5.2 GAP Analysis

本节检验节点级路由是否具有经验依据。若不同模型在全部节点上的能力排序基本一致，那么固定选择同一模型即可，进一步细化选择粒度缺少收益空间。实验因此比较 Best Single、Node Oracle 与 Query Router，同时按节点类型分析固定模型质量。Best Single 在当前评价范围内选取平均质量最高的固定模型；Node Oracle 根据每个节点的事后评分选择最佳模型，只作为上界；Query Router 使用原始问题表示选择模型，不显式区分任务内节点职责。

所有方法使用相同的 493 个主要节点和已采集模型回答。整体 GAP 定义为 Node Oracle 与整体最佳固定模型的质量差；类型内 GAP 则以该类型的最佳固定模型为基线。两种 GAP 回答不同问题：整体 GAP 同时包含类型间和类型内异构性，类型内 GAP 进一步检验仅知道任务类型后是否仍存在选择机会。表 5-2 和表 5-3 分别列出整体比较与类型内能力分布。

表 5-2　独立确认集上的整体路由机会

| 方法 | Quality | 相对 Best Single 的质量差 |
| --- | --- | --- |
| Best Single（large） | 0.4483 | 0.00 pp |
| Query Router | 0.4442 | −0.41 pp |
| Node Oracle | 0.5781 | +12.98 pp |

表 5-3　节点类型内的模型能力差异

| 节点类型 | medium | large | coder | Oracle | 类型内 GAP |
| --- | --- | --- | --- | --- | --- |
| Extraction | 0.3731 | 0.5959 | 0.3782 | 0.6943 | 9.84 pp |
| Reasoning | 0.1900 | 0.1500 | 0.1700 | 0.2700 | 8.00 pp |
| Verification | 0.5200 | 0.4550 | 0.5900 | 0.6200 | 3.00 pp |

整体上，Oracle 的质量为 0.5781，超过最佳固定模型 12.98 pp，而 Query Router 未超过该固定基线。这表明现有查询级预测器没有充分利用面板中的选择机会。更重要的是，三种主要节点的最佳固定模型不同：large 在抽取上最高，medium 在推理上最高，coder 在验证上最高。若将一个完整问题交给同一模型，就难以同时匹配这些不同需求。此结果直接支持将路由对象从完整查询下降到任务节点。

类型内仍保留正 GAP。抽取、推理和验证的 GAP 95% 置信区间分别为 [5.15, 15.10] pp、[3.00, 11.00] pp 和 [1.00, 5.50] pp。即使采用每种类型各自最强的固定模型，也不能覆盖所有节点上的最佳回答。因此，节点类型有助于解释异构性，但并不是全部解释，问题内容与具体实例仍影响模型相对表现。4 个 transformation 节点上所有模型均获得 1.0，样本过少，仅保留为探索性结果。

Oracle 以事后标签选择，天然比可部署预测器掌握更多信息，因此正 GAP 不能直接证明这些机会可学习。Query Router 的不足也应限定于当前表示、训练数据与模型池，不能推导为所有查询级方法均无效。本节结论是：当前复杂任务面板呈现明确的类型间能力差异和剩余类型内机会，节点级选择具有可检验的动机；是否能够实际利用这些机会，由下一节的冻结路由确认回答。

## 5.3 Node-level Routing

本节直接检验节点级模型选择的有效性。实验比较 Always Large、Query Router、Static Capability、Frozen Node Router 和 Node Oracle。Static Capability 使用开发面板中的全局模型画像与固定效用，当前实现并非按节点类型单独构建的能力表；它在确认集中与 Always Large 产生相同选择。Frozen Node Router 对静态 DAG 中的节点分别决策，执行期间不更新预测器、不使用反馈，也不进行失败重试。因此，本节的质量差异对应初始选择策略，而非恢复预算增加。

五组共享同一完整模型回答面板。节点评分按冻结规则计算，成本在任务内部按真实请求去重。例如，一次抽取回答可能对应多个评分节点，不能将同一次请求重复收费。主要指标为平均节点质量、每任务 tokens 和每任务累计服务时间。表 5-4 给出结果；Oracle 的资源数据对应其事后选择结果，不代表在线可实现的同等收益。

表 5-4　冻结节点路由的独立确认结果

| 方法 | Quality | Tokens / task | Service time / task（s） |
| --- | --- | --- | --- |
| Always Large | 0.4483 | 4991.02 | 11.710 |
| Query Router | 0.4442 | 4985.33 | 10.185 |
| Static Capability | 0.4483 | 4991.02 | 11.710 |
| Frozen Node Router | 0.5132 | 4856.43 | 7.787 |
| Node Oracle | 0.5781 | 5217.67 | 6.432 |

Frozen Node Router 相比 Query Router 提高 6.90 pp，95% 置信区间为 [3.43, 10.48] pp；相比 Always Large 提高 6.49 pp，区间为 [3.86, 9.13] pp。与此同时，相比 Query Router，每任务减少 128.90 tokens，区间为 [84.50, 175.42] tokens；累计服务时间减少 2.398 秒，区间为 [1.356, 3.496] 秒。按点估计计算，token 降幅约为 2.59%，服务时间降幅约为 23.54%。因而，本次收益不是通过增加执行次数获得，而是在相同初始执行设置中改善质量和资源使用。

选择分布为这一结果提供了机制上的解释。Frozen Node Router 在 493 个主要节点中分别选择 medium 93 次、large 203 次、coder 197 次；Query Router 对应为 133、276 和 84 次。节点路由增加了 coder 的使用，减少了将所有职责集中交给 large 的倾向。不过，选择分布本身并不构成效果证据，必须结合相应类型的实际质量。节点路由在抽取、推理和验证上的质量分别为 0.5959、0.2200 和 0.5800，Query Router 分别为 0.4974、0.2000 和 0.5150。

类型内结果也揭示了边界。抽取节点路由达到该类型最佳固定模型水平，但没有恢复其类型内 Oracle GAP；推理高于最佳固定模型 3 pp，类型内恢复率点估计为 37.5%，其区间仍较宽；验证为 0.5800，略低于 coder 固定选择的 0.5900。因此，整体收益主要支持对异质节点采用不同选择，并不能写成每个类型都稳定超越类型内最佳模型。

以整体最佳固定模型为基线，质量 GAP Recovery 为 50.0%，95% 区间为 [32.81%, 65.28%]。这一质量恢复率与此前基于效用计算的恢复率不是同一指标。本节据此确认：在冻结开发设置和审计后的独立任务上，节点级路由优于当前查询级基线，同时减少去重 token 消耗和累计服务时间；其结论适用于条件节点基准，不直接等同于端到端任务成功率提高。

## 5.4 Feedback Learning

静态节点预测器仅使用开发阶段知识。本节考察执行后积累的历史信息能否改善后续决策。实验在相同确认面板上按固定任务顺序回放，比较 Static Node Router、类型记忆 Feedback V0 和状态条件化 Feedback V1。反馈记录只在相应调用发生后更新，未来节点标签不提前进入决策。V1 初始记忆以节点类型、问题长度分桶和模型为键，失败恢复另维护类型与模型对应的成功统计；初始融合权重为 0.3，恢复融合权重为 0.5。

该实验评价的是反馈条件化选择及有限回退的组合。V0 主要改变初始选择，V1 还包含一次基于恢复记忆的替代模型调用。因此，V1 相对静态方法的全部提升不能单独归因于记忆统计更准确，也包含额外执行机会的作用。主要指标仍为节点质量；资源比较使用有效成本估计，将平均被选调用消耗乘以调用倍率，以反映额外回退，避免只看最终回答的开销。

表 5-5　反馈学习的顺序回放结果

| 方法 | Quality | 相对静态质量差 | 调用倍率 | 有效 tokens / node（估计） |
| --- | --- | --- | --- | --- |
| Static Node Router | 0.5132 | 0.00 pp | 1.000 | 1765.0 |
| Feedback V0 | 0.5152 | +0.20 pp | 未单列 | 未单列 |
| Feedback V1 | 0.5558 | +4.26 pp | 1.487 | 2677.5 |
| 冻结排序回退，理想失败检测 | 0.5497 | +3.65 pp | 1.487 | 2676.0 |

Feedback V1 将质量从 0.5132 提高到 0.5558。相对于 V0，平均节点质量差为 4.06 pp；结果文件另报告按任务平均差进行聚类重采样的区间 [2.20, 6.00] pp。两者聚合权重不同，区间不应解释为完全相同估计量的精确区间。V1 相对 V0 改变了 224 次最终选择，其中 20 个节点质量提高，未记录到质量降低。类型记忆 V0 的增益较小，说明仅根据粗粒度类型频率修正初始估计，在当前面板上的帮助有限。

状态条件化记忆能够区分不同长度桶中的执行经验，失败记忆则将初始执行与恢复情境分开。它们提供了可能的改善机制：静态预测相近的候选可由历史成功表现重新排序，而已失败状态下的候选选择不再完全沿用初始排序。不过，比较没有单独隔离所有因素，不能据此断言状态分桶、记忆融合和额外回退各自贡献多少。V1 与相同调用倍率的冻结排序回退相比，质量高约 0.61 pp，也只能作为描述性补充，缺少该对照的独立显著性检验。

质量改善伴随资源增加。有效 token 成本从约 1765.0 增至 2677.5 tokens/node，增幅约 51.7%；估算服务时长从 2.717 增至 4.731 秒/node。该成本不是逐次失败与回退的精确累计，而是聚合近似。反馈回放还使用离线评分判定初次失败，因此它不能证明在线系统具有同等准确的失败感知能力。

本节支持的结论是：在既定执行顺序和可用结果反馈下，状态记忆与记忆驱动回退的组合能够改善后续节点选择。该机制提供质量优先场景中的候选策略，但不是无成本提升，也尚不能被解释为在真实噪声反馈环境下已独立确认的在线学习收益。

## 5.5 Adaptive DAG

本节将重点从普通节点的平均预测能力转向失败恢复。动态机制需要回答两个问题：哪些异常值得触发额外执行，以及模型切换仍不能解决的节点是否可以通过结构分解恢复。实验分别分析失败检测、类型门控和 failure-aware decomposition，避免把“增加调用”本身等同于有效适应。

检测策略在同一节点面板上比较无验证器、全局验证器和 Type-aware Gate。验证行为由已有测试床上的混淆统计抽样回放，并非对面板中每个输出重新真实验证。类型门控将验证驱动重路由限制在 verification 类型，reasoning 节点保留初始选择；实现包含拒绝后的候选切换及再次验证，部分路径会继续切换。主要指标为最终质量、重路由次数、误触发和验证调用数。

表 5-6　失败检测与类型门控回放

| 策略 | Quality | 重路由次数 | 误触发重规划 | 验证调用数 |
| --- | --- | --- | --- | --- |
| 无验证器，静态选择 | 0.5132 | 0 | 0 | 0 |
| 全局验证器 | 0.5132 | 231 | 47 | 439 |
| Type-aware Dynamic | 0.5254 | 186 | 35 | 302 |
| 理想失败检测回退，参考 | 0.5497 | — | — | — |

全局验证器产生额外执行，却没有提高净质量。类型门控将质量提高至 0.5254，相比静态增加 1.22 pp，同时减少了相对全局策略的重路由和误触发。这说明验证器的使用范围会影响收益：在错误识别不可靠的节点上普遍触发干预，可能抵消被修复节点带来的提升。全局策略记录 9 个恢复节点，类型策略为 7 个，但前者净质量没有提高，进一步说明恢复数量必须与干预造成的损失联合解释。

不能将门控描述为准确失败检测已被解决。已有验证测试床中，v1.1 在 17 个分解样本上的错误召回仅 18.18%；在 40 个 verification 样本上的错误召回为 100%，同时误报率也为 100%。门控回放使用另一组明确写入代码的类型条件拒绝概率，因而不应把 v1.1 的全部诊断指标直接归因于门控结果。混淆矩阵近似忽略实例级相关性，单次固定种子结果也不代表多次部署的稳定收益。理想失败检测下 0.5497 的质量只能表明检测可靠性仍限制可达到的恢复效果。

结构恢复在 20 个困难 reasoning 节点上进行真实调用比较。样本来自模型选择难以解决的失败集合，不代表所有任务的随机样本。实验比较允许相同常数与运算符的直接重问，以及事实对齐、关系规划、表达式生成和检查组成的失败感知分解。最终质量以确定性执行值是否匹配标准答案判断，不以模型自评作为成功依据。

表 5-7　困难推理节点的结构恢复

| 方法 | 成功恢复 | 恢复率 | 证据范围 |
| --- | --- | --- | --- |
| 扩展表达式语言后直接重问 | 0/20 | 0% | 同一困难样本集 |
| Failure-aware Decompose | 6/20 | 30% | 同一困难样本集，真实调用 |
| 固定分解模板，历史参考 | 0/10 | 0% | 不同原始执行条件，不作严格配对 |

分解恢复了 6 个节点，而直接重问没有恢复。合理的机制解释是，显式对齐事实的实体、期间和单位，并独立组织关系，能够纠正单次表达式生成中的部分语义错误。但该小样本结果没有证明分解普遍优于简单调用，也不能把 30% 当作全部失败任务的普适恢复概率。分解中的语义验证与实际结果仅有有限一致性，最终判断仍依赖执行结果。

本节结论是，动态适应的价值主要体现在可定位失败后的有条件恢复：类型门控减少无效干预，结构分解对部分难例提供超出换模型的恢复路径。检测不可靠时，增加验证和重规划可能没有净收益；因此，动态模块应以失败恢复证据和新增开销共同评价，而不是要求它在所有正常节点上无条件提高质量。

## 5.6 Graph Forest

Graph Forest 面向相关追问中的重复计算，与单轮节点路由承担不同任务。本节检验在原始材料未变、用户只修改部分假设时，能否复用历史图中不受影响的节点。实验从已有任务中选择 20 个满足抽取结果条件的样本，追问将第一个事实的假设值提高 10%。历史抽取节点被保留，仅重新执行 reasoning 和 verification 路径。样本具有筛选条件，结果限定于这种局部假设修改场景。

实验比较已有全链调用记录与复用后真实执行的追问调用。评价指标为逻辑节点复用率、调用减少比例、token 减少比例，以及新链是否可执行、结果是否响应修改。后两项是执行行为指标，不是独立答案正确率。历史图保存输入引用、输出、模型、依赖与版本，使改变能够定位到相应计算路径，而不需要重新处理全部原始材料。

表 5-8　20 个追问任务的历史图复用

| 指标 | 结果 | 解释 |
| --- | --- | --- |
| Reuse Rate | 50% | 每任务复用两个抽取逻辑节点的记录口径 |
| 复用抽取节点总数 | 40 | 历史节点直接保留 |
| 基线调用数 / 复用调用数 | 80 / 40 | 按原实验记录的调用计数 |
| Call Reduction | 50% | 由上述调用计数计算 |
| Token Reduction | 91.4% | 追问调用与历史基线消耗比较 |
| 新链可执行 | 19/20 | 表达式生成并完成计算 |
| 结果响应修改 | 19/20 | 新结果随假设变化 |
| verifier_accept 为 true | 0/20 | 不支持已通过独立语义核验的结论 |

结果显示，原实验计数下调用减少一半，token 消耗减少 91.4%。token 降幅大于调用降幅具有明确的工作负载原因：原始材料抽取通常携带较长输入，而修改假设后的推理只需要较短事实表示。省去长上下文处理可能比单纯减少短调用节约更多 tokens。因此，图复用收益不仅取决于复用多少节点，也取决于被跳过节点原本承担多少材料处理。

这些资源数据存在两项重要口径限制。第一，调用基线按逻辑链记录为 80 次，而原始节点面板中的多个抽取节点可能共享一次请求。该记录口径不等同于 5.3 节严格去重的物理调用数，50% 应保留为原试验报告值，不能直接推广为任意部署中的请求节约率。第二，token 对照使用历史执行记录与新的追问调用，并非两个完全对称、同轮重新执行的在线组；异常路径对消耗的记录也影响完整核算。因此，91.4% 是特定协议下的观测节约，不是已经完成严格质量等价控制的普适结果。

19 个任务能够计算出新值且响应假设变化，说明局部重算链条可以运行，但数值改变不自动意味着新答案正确。结果文件中没有 verifier_accept 为 true 的样本，故不能据此宣称 95% 的追问质量或已保持语义正确性。已有图森林机制演示还包括保存历史图、按任务标识检索、保留旧版本及使后继失效，这些支持执行复用机制的存在，但不构成大规模语义图检索的证据。

本节确认了历史图对避免重复材料处理的价值，并显示较强的资源节约潜力。其结论应限定为多轮局部修改条件下的机制与资源证据；单轮静态质量提升不能归因于图复用，追问质量保持也仍需独立正确性评价支持。

## 5.7 Multi-objective Optimization

不同应用对质量和开销的偏好不同。本节将 Static、Feedback 和 Dynamic 放在统一 Q/C/L 视角下比较，检验是否存在一个在所有目标上都占优的策略。候选来自相同主要节点面板，按质量最大化、成本和服务时长最小化进行非支配筛选。Oracle 及依赖完美失败检测的策略不进入可执行候选前沿，以避免让事后标签决定策略选择。

动态策略包含额外回退和验证，不能仅使用最终选中回答的成本。因此，现有分析以平均被选调用 tokens 乘执行倍率，并对适用策略加入验证开销估计。验证调用按每次 600 tokens 估计，服务时长以平均节点时长乘调用倍率近似。缺少延迟记录的 Type-aware Dynamic 仅进入质量—成本比较，不填造三目标数据。表 5-9 保留上述估计口径。

表 5-9　候选策略的质量与有效资源消耗

| 策略 | Quality | 有效 tokens / node | 有效服务时长（s/node） | Pareto 状态 |
| --- | --- | --- | --- | --- |
| Static Node Router | 0.5132 | 1765.0 | 2.717 | 二目标与三目标前沿 |
| Feedback V1 | 0.5558 | 2677.5 | 4.731 | 二目标与三目标前沿 |
| Type-aware Dynamic | 0.5254 | 2815.6 | 未记录 | 二目标中被支配 |
| 理想检测 Dynamic | 0.5497 | 2676.0 | 4.663 | 诊断参考，排除 |
| Node Oracle | 0.5781 | 不作可执行比较 | 不作可执行比较 | 事后上界，排除 |

Static 和 Feedback 构成当前候选集合的 Pareto 前沿。Static 的质量较低，但资源消耗更少；Feedback 的质量更高，同时需要额外成本和服务时间。两者均无法在所有目标上支配对方。Type-aware Dynamic 相比 Static 有质量增益，但在当前估算下比 Feedback 成本更高而质量更低，因此在二目标比较中被 Feedback 支配。该结果说明动态恢复有效与成为特定工作负载的最优整体策略并不是同一件事。

质量约束下的选择进一步说明应用偏好的作用。当最低质量为 0.50 时，Static 已满足约束且成本最低；当要求提高至 0.52 或 0.55 时，当前候选中选择 Feedback。这里的阈值用于展示已有策略之间的约束选择，不是对确认集重新调训练参数。Pareto 结论也仅相对于已列候选成立，不意味着在全部可能图结构、路由器和执行计划中达到了全局最优。

Oracle 的资源不能被解释为同时可达的最优质量、最低成本和最低延迟。部分聚合文件分别取质量最优及资源最小值，这可能对应不同模型，无法构成同一个可执行计划。为避免这种混合，本节只保留 Oracle 质量上界，不将其资源向量用于方法优越性论证。聚合文件中的固定模型标识还需与模型列顺序一致；本节固定模型实测比较采用 5.3 节经核对的结果，不沿用存在标识歧义的额外条目。

现有 Pareto 结果同样受成本近似影响。平均最终调用消耗乘倍率未必准确反映先失败、后回退的实际消耗，不同模型调用顺序也影响服务时间。Feedback 的失败触发在回放中使用可评分结果，因而虽被策略文件列入候选，也不能称为已验证可直接在线部署的方案。没有跨随机种子前沿稳定性或完整墙钟时延测量时，不对细小资源差异作显著性解释。

本节结论是：质量与资源开销之间存在实际取舍。Static 适合较低质量门槛下的节约型选择，Feedback 在当前候选中提供更高质量选项；Pareto 分析将这种差异显式化，而没有把质量提高自动等同于整体效率提高。

## 5.8 End-to-End Evaluation

最后，本节检验各模块能否在同一任务面板上组成完整决策链。实验比较 Static Only、Static + Feedback 和 Full Adaptive DAG。前两组分别采用冻结节点选择与状态记忆驱动选择及回退；完整组结合共享反馈状态、类型门控和困难推理节点的分解恢复。Graph Forest 的追问试验作为多轮部分单独报告，不混入单轮质量平均值。

该实验的准确性质是 formal replay：基础节点输出来自真实采集，但验证判定和分解恢复由组件统计量抽样构造，并非三个系统重新完整执行 100 个用户任务。随机种子固定为 20260915。综合脚本以最终 reasoning 节点正确作为 Task Success，以 493 个节点的平均评分作为 Quality。因此，即便最终推理正确，也不表示所有抽取与验证步骤均正确，标准事实条件下的成功率不能等同于真实输入传播下的成功率。

表 5-10　综合三臂 formal replay

| 方法 | Task Success | Quality | 有效 tokens / node（估计） | 服务时长代理（s/node） |
| --- | --- | --- | --- | --- |
| Static Only | 22% | 0.5132 | 1765.0 | 2.717 |
| Static + Feedback | 27% | 0.5558 | 2677.5 | 4.731 |
| Full Adaptive DAG | 56% | 0.5801 | 3071.0 | 3.575 |

Static + Feedback 相比 Static Only 的任务成功率提高 5 pp，完整组进一步达到 56%，较反馈组提高 29 pp。相应节点质量依次为 0.5132、0.5558 和 0.5801。完整组相对反馈组的质量增量为 2.43 pp，小于任务成功率增量，这是因为任务成功率只关注 100 个最终推理节点，而总体质量同时平均抽取与验证节点；二者分母与含义不同，不能互相替代。

从记录的过程变量看，完整组产生 308 次验证调用、108 次重路由和 73 次分解触发，其中 29 次被抽样为成功恢复。任务成功率的大幅提高与这 29 次推理恢复直接相关。分解恢复概率设置为 0.55 × 0.60，即假设困难样本中相应类别占比为 55%，该类别恢复率为 60%。后者以局部小样本证据为依据，不能等同于在新增 73 个节点上真实测得的成功概率。

表 5-11　完整组的内部过程与证据属性

| 过程指标 | 记录值 | 证据性质 |
| --- | --- | --- |
| 验证调用 | 308 | 按类型条件混淆概率抽样 |
| 重路由 | 108 | 综合回放执行逻辑 |
| 分解触发 | 73 | 回放中判定的困难推理 |
| 分解恢复 | 29 | 按组件恢复概率抽样 |
| 误触发重规划 | 28 | 抽样判定与离线标签比较 |
| 追问复用 | 50% | 独立 20 任务追问试验 |

完整组的 0.5801 略高于固定模型选择 Oracle 的 0.5781，不意味着超过绝对质量上界。该 Oracle 只允许从原有三个模型回答中选择，分解产生的是原回答集合之外的结果，二者候选空间不同。尤其在综合回放中，抽样恢复的推理节点直接设为正确，因此超过选择上界也部分来自建模规则。以静态路由为基线计算的 Oracle-gap Recovery 因而可能超过 100%，这一数值不是实际失败恢复率，不能作为额外性能保证。

资源比较也需保持克制。完整组有效成本约为 3071.0 tokens/node，高于反馈组和静态组，支持质量收益伴随额外开销，而非整体成本下降。其服务时长代理低于反馈组，但该估计未完整计入验证和分解调用的真实耗时；不能由 3.575 秒直接得出完整系统更快的结论。调用倍率也未涵盖全部分解和验证开销，不能替代实际物理请求计数。相关数值提供聚合分析输入，不构成严格端到端性能测量。

综合脚本还存在影响因果解释的约束：完整组共享反馈状态，但并非在反馈组全部逐节点结果上单调增加模块；部分分支采用不同回退路径。恢复结果按聚合数量写回困难节点，未保留每个抽样恢复节点完整的真实执行轨迹。因此，三臂递增结果支持模块组合在既定建模假设下具有改善潜力，不能精确分解每一模块的独立贡献，也不能声称所有错误传播和反馈闭环都已在线验证。

Graph Forest 在本节框架中的职责仍是多轮计算复用。单轮失败恢复改变当前任务的执行路径，历史图复用减少相关追问中的重复材料处理；二者在时间范围和评价指标上互补。现有 20 任务追问试验报告 50% 的复用与调用减少以及 91.4% 的 token 降幅，但其质量和调用口径限制仍按 5.6 节保留，不能用这些资源结果为单轮综合模拟提供额外正确性背书。

总体而言，实验最强的独立证据来自冻结节点路由：相对当前 Query Router，质量提高 6.9 pp，并减少相同调用面板上的 token 消耗与累计服务时间。反馈与动态恢复的组件结果说明历史经验和结构修复能够补充静态选择，图森林展示多轮复用机制；综合回放进一步呈现组合后的质量与成功率提升。上述证据共同支持框架设计的合理性，但完整在线系统的真实失败检测、错误传播、质量保持与端到端资源收益仍不能由现有 formal replay 替代。
